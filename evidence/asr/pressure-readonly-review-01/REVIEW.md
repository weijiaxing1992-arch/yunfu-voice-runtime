# 2000 路失败记录的只读审查

本轮未运行压测、未修改候选源码。原记录是 Darwin arm64 同机隔离实例的 relay 测试，不能认证 Linux 生产容量，也不能用 ASR 的单路测试覆盖此项失败。

## 已确认的事实

- 2000/2000 路建立，双向各发送 1,000,000 包，合计 2,000,000 包；唯一接收 456,233 包，接收率 22.81165%，未接收 1,543,767 包。每个方向都足额发送 500 包，而接收仅 99–125 包；端到端媒体验收确实失败。
- 发生器接收 API 调用 456,489 次，恰好等于唯一接收 456,233 加 256 次尾窗结束超时；reader_errors=0、write_errors=0、invalid/duplicate/unknown=0。每个接收协程在发送结束后的 500 ms 尾窗超时一次，不能误报为 256 次提前读取失败。
- 固定 8 个发送工作者，128 组共享端点对应 256 个 RTP 接收工作者；并非每通话一个接收 OS 线程。portable_udp 的 2,000,000 次发送统计是 Go UDP API 调用，不等于 Linux mmsg 批次数或可直接比较的内核调用数。
- 媒体分片合计 rx=tx=921,898，接收批次 921,898、接收调用 1,843,796、最大批次 1；符合便携路径每次读到一包、再读到 WouldBlock 的统计。它反映收发粒度，没有直接证明内核队列饱和或某个具体丢包位置。
- 发生器约 12 CPU 秒、Rust 合计约 6.03 CPU 秒均为整进程累计，包含建立阶段，不能直接除媒体 10 秒得到精确媒体核占用，更不能证明 10 核耗尽。发生器缺少媒体窗口开始的同口径资源快照。

## 两个可执行的诊断修复

1. **失败分支也应等待有界的新鲜终态统计。** 当前 `control/internal/server/benchmark_runner.go:604–613` 在发生器错误后只取一次 HTTP 状态就退出。本件发生器退出时间为 04:58:24.773396Z，最终 HTTP 时间为 04:58:24.774525Z，但 10 份工作者统计实际来自 04:58:24.038104–044299Z，早了约 729–735 ms。最终 HTTP 新鲜不代表媒体缓存已刷新；2000 media_active 与 0 control_active 的差异也不能单凭此认定资源泄漏。下一增量可复用已有 5 秒收敛窗口，独立等待所有工作者的统计时间超过发生器退出时间，记录是否收敛及采样失败原因；原压测状态始终保持 failed，不能因清理成功改为 passed。

2. **未提供的 socket 丢包计数应显示未提供。** `benchmark_processing.go:73` 累计了 socket_rx_drops，却未保留 socket_drop_counter_supported。本件所有 10 个工作者的支持标志均为 false，页面 `web/tests.js:119` 仍显示数字 0，仅在说明中解释限制。下一增量应把支持数量及逐工作者可用性带进采样；完全不支持显示“未提供”，部分支持显示覆盖范围，不让读者把未测量误读为无丢包。

## 性能优化的下一步

先补齐观测，再选择优化点：记录每个端点与媒体 socket 的实际 SO_RCVBUF/SO_SNDBUF、可用的丢弃指标、工作者在媒体结束后的新鲜计数；发生器记录媒体窗口前后 CPU 差值及每批发送耗时、首包/尾包相对计划的迟到分布。`media_schedule.go:160–189` 的 generator_late_ticks=0 只表示相位开始时未晚于 2 ms，并未测到同相位后续每个包的排队和发送时间。

随后再安排互相独立的诊断对照：发生器端点直连、当前 relay、Linux mmsg 分别记录相同逐流 500 包与期限断言，保持端到端零缺包门槛。直连若也失败，只能说明发生器/本机收发路径尚有瓶颈；直连通过也不单独定位 relay 中的丢失点。性能测试需要真实运行后才给结论，本轮不预估通过率。

当前证据不能把 2,000,000 → 921,898 → 456,233 的差额归因到指定一跳，也不能断言是网络、CPU、线程或某个系统调用的单一问题。原件保留 failed。
