# RustSwitch 0.2：性能优化与验收记录

日期：2026-09-05。架构继续采用 **Rust 媒体核心、Go 控制面、C/C++ 原生库适配接口**。

本轮完成了可构建、可回归的优化版本。最终本机 1000 路、60 秒测试完整收发 5,999,904 个 RTP 包，通话与媒体分配正常释放。**万路媒体验收尚未通过，Linux 运行性能尚未验证。**

用户将稍后提供 Linux 服务器。本轮交付源码、构建结果、原始测量记录和 Linux 验收工具；不以配置上限、累计接通数或交叉编译检查代替容量结果。

## 代码变化

| 范围 | 已实现 | 作用与边界 |
|---|---|---|
| Rust 媒体寻址 | 固定会话槽位、带代次的 socket 就绪标识、索引去重队列 | 成功转发路径避免会话哈希查询；旧就绪事件不能操作端口复用后的新通话 |
| Linux 接收 | 预分配 8×2048 字节缓冲，非阻塞 `recvmmsg`，保留截断与 socket 丢包信息 | 减少批量到达时的接收系统调用；继续读到 WouldBlock，避免丢失边沿就绪；本机 Mac 走兼容路径 |
| UDP 对端 | 可选连接式 UDP；相同 183/200 端点不重复连接；端点变化清理旧待发包 | 使用固定对端发送路径；不支持自动 NAT 学习；内核来源过滤可能早于应用计数 |
| Go 准入 | CPU、可观测丢包增量、控制积压、统计过期共同控制新分配 | 按分片关闭准入，连续三个健康样本后恢复；已有通话连接与释放继续执行；不能保证发生拥塞时无丢包 |
| 控制调度 | 分配与连接/释放分别使用 64 项队列，优先处理已有呼叫操作 | 限制新 INVITE 洪峰对接通和结束操作的排队影响；保留超时与进程代次保护 |
| 定时器 | 带索引的可取消堆，同键原位更新，接通/ACK/结束主动删除 | 短通话不再堆积最长通话时长的废弃项；必要的 SIP 缓存与回收定时器仍有限保留 |
| 发生器 | 分方向/逐流校验、端口范围与打散分配、可配置相位、共享端点诊断、连接式发送 | 报告实际提交量与名义负载比；SSRC、序列、时间戳、内容和来源共同验证；减少每包锁和临时对象开销 |
| 验收证据 | 二进制哈希、配置、并发采样、事件并发重建、资源清理与日志持久化检查 | HTTP 采样缺失和日志证据缺失不能被默认为通过；失败记录保留 |
| Linux 采集 | 持续写入主机与应用 JSONL 指标，内存占用不随时长累积 | 只读，不修改系统配置；实际 Linux 运行待验证，不自动生成容量通过结论 |

### 最终千路结果的含义

[最终原始报告](benchmarks-v0.2/final-dialudp-1000-60s.json) 与 [服务端证据](benchmarks-v0.2/final-dialudp-1000-60s.evidence.json)：4 个 Rust 工作进程，双方使用连接式 UDP，发生器每路独立四个端口，设定 500 CPS，建立阶段约 2.003 秒。60 秒的名义包数为 6000000，实际提交比例为 99.9984%。发生器唯一接收数与 Rust 收/发计数均为 5999904。

没有观测到重复包、内容错误、发送错误、异常 BYE 或挂断失败；事件重建及状态采样均确认 1000 路同时建立，结束后控制面呼叫与媒体分配归零。4001 条当前运行事件已同步，丢失事件为零。发生器仍记录到调度迟到，它不等于服务器转发时延。

这次通过发生在减少发生器热路径开销和避免重复 UDP 连接等改动之后，但单次前后测量不足以证明丢包根因或量化独立优化收益。此前 60 秒测试未收到 6560 包，媒体收发计数均为 5995573，计数缺口同时存在于媒体接收前和发送后；这不是已定位具体内核/网卡故障的证据。失败结果没有被最终通过覆盖。

### 万路结果的含义

[共享端点报告](benchmarks-v0.2/grouped-10000.json) 中，发生器使用 512 组、共 2048 个 UDP socket，服务端仍分配每路四个媒体端口。事件重建证实曾同时建立 10000 个会话，但实际发送量只有名义 5000000 包的 **39.09584%**，只收到 728 包。另有 9641 次清理失败，清理观察结束时控制面仍有 3001 个活跃会话，随后本地编排终止了该测试服务。

该测试高负载期间 HTTP 采样未覆盖峰值，不能仅凭采样图推断未达到或维持了某一并发。事件原文证明的是会话数量，不证明万路持续媒体可用。专用端点万路请求测试同样失败。最终代码在本机没有再次执行万路容量测试，需在独立 Linux 压测机与目标机之间继续验证。

有效的 5000 路终端直连诊断也出现丢包，说明发生器或同机网络路径存在额外限制；它不能排除 Rust 服务自身的瓶颈。现有 Mac 计数不足以确定最终根因。

## 历史诊断纠错

源码审计发现旧 `--go-relay` 标志只更改报告标签，没有建立实际 Go 转发路径。已删除该标志，并将 [历史 JSON](diagnostic-local-1000-go-relay.json) 标记为无效证据；撤回由此得出的“问题并非 Rust 独有”推断。旧 0.1 记录已追加纠正，0.2 源码包替代旧包。

## 下一阶段与交付边界

按 [Linux 验收步骤](linux-validation.md) 先测 1000、5000，再测 10000 路；同时记录实际包率、同时建立数、各媒体进程 CPU、socket 丢包、NIC/UDP 全局计数和资源回收。独立验证集中突发、持续呼叫周转、故障与过载。最终再测 P99/P99.99 转发时延和长时间稳定性。

当前没有实现 `sendmmsg`、io_uring、AF_XDP、DPDK、生产级 C/C++ SIP 提供器、完整 FreeSWITCH 模块兼容或跨机接管。现有 C 编解码插件已实际验证，协议适配头仍是预留契约。整机或控制进程故障下保持存量通话、零业务损失与 RPO=0 均未实现；完整能力边界见 [README](../README.md)。
