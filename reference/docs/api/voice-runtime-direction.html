云蝠 Voice Runtime：研发方向与验收标准

自文档1.9起，项目定位为面向语音智能体的高性能实时语音内核。沿用 RustSwitch 的工程名称、配置、程序和现有接口，优先兼容电话智能体实际使用的 FreeSWITCH 接口。首期交付以电话与AI媒体闭环验收，完整PBX功能及全部FreeSWITCH模块复刻不作为首期门槛。

本页依据本轮确认的需求调整优先级。原有FreeSWITCH目录、差异、失败记录和完整契约标准仍保留，可用于迁移评估；改变首期范围不会把未实现项变成绿色，也不会改变完整兼容统计的分母。

本文档包 1.13.0 包含已验证的内部 RX 收音，并保留 1.12 已有的 G.711 图、PCM 轮次和 RVA1 下行。实际安装版本须通过 GET /v1/docs 及部署回执核对，不能从文档包版本推定已安装。下文保留本批候选测试的冻结身份与通过范围；内部上行基础已验证，供应商 ASR/TTS 仍未接通。

完整长期目标的20节、17项V1能力、10命令/11事件及M1—M4逐项门槛，见Voice Runtime V1验收合同。这是未完成目标的持续验收依据，不修改FreeSWITCH对照的原始ID或绿色。

成功标准与测量前提

在相同服务器、相同音质、相同业务功能和安全配置下，提高有效稳定媒体并发并降低每通话成本。Rust语言、共享端口、关闭录音或把协议处理移到外部进程，都不能单独作为性能提升证据。

初始研发目标 判定口径 当前结论
完整Voice Agent稳定并发为现网1.5倍，进阶2倍 冻结同硬件、线路、编码、ptime、录音与安全配置，含真实ASR/TTS连接成本 目标待基线冻结，尚未证明
同并发总CPU下降至少30% 计入媒体、Go控制、SIP适配、录音、内核及保留的FreeSWITCH进程 尚未证明
同并发内存下降至少30% 使用相同音频缓冲时长、功能与录音策略 尚未证明
发送调度迟到P99不高于2ms、P99.9不高于5ms 已具备发送条件的包，从计划时刻到成功交给内核的迟到，失败另计 尚无该完整指标验收
72小时混合负载 联合建呼、挂机、抢话、打断、录音和故障注入 尚未执行

这些是研发门槛，不是当前能力承诺。此前500／5000路转发测量不能折算成完整Voice Agent容量。1.5～3倍仅可作探索范围，不作为宣传数据。

发送调度迟到、RTCP interarrival jitter、抖动缓冲等待、TTS预缓冲、网络传输和终端播放延迟分别计量，不使用一个“延迟”数字代替整条链路。最终可用并发要求CPS、媒体、音质和尾延迟同时达标。

技术与所有权约束

层 责任与边界
Rust实时媒体 RTP、音频时钟、编码／解码、按需重采样、播放时间线、打断和音频分发
Go业务控制 呼叫任务、路由、租户、智能体编排、幂等命令、事件及业务接口
SIP接入适配 优先复用成熟实现；当前受限Go提供器继续验证，Sofia/PJSIP等接入另设里程碑
C/C++编解码与DSP 通过受控接口复用成熟库；不要求为了纯Rust重写所有Codec
部署与测量 Linux优先；固定CPU、网卡、内核、NUMA及资源限制

一个媒体会话由一个固定Worker修改状态；桥接双腿尽量同Worker，首期不自动迁移活动媒体。禁止每通话创建操作系统线程。当前采用多个独立媒体进程，每进程一个媒体事件循环；故障影响范围按进程所属会话披露，不承诺进程崩溃只影响一通电话。

Worker不等待数据库、磁盘、HTTP或模型服务。重DSP任务使用有容量、并发和截止时间的独立执行池。通用异步运行时不能替代媒体预算管理；Tokio的阻塞池对CPU任务需要额外限制，并且已经运行的阻塞任务不能简单依靠abort取消。Tokio官方文档

收包、发送和控制各有公平预算，挂断／打断有专门配额；控制洪峰也不能饿死媒体。CPU亲和性、IRQ、RSS/RPS/RFS/XPS和NUMA按实际测量选取，避免无依据全部启用。

音频对象与媒体图

统一AudioFrame的接口、时间和生命周期；允许保留输入或目标分支所需的采样率。帧明确采样率、声道、样本格式、有效样本数、媒体时间和来源状态。G.711可以保持8k PCM，ASR需要16k时仅在ASR分支转换；TTS的24/48k音频在电话输出分支转换。同一区间避免重复解码和重复转换。

G.722音频为16kHz而RTP时钟为8kHz；Opus的RTP时钟为48kHz。编码元数据必须分别保存这两个值。RFC3551、RFC7587

同Worker消费者优先借用或使用缓冲池句柄；跨线程可以选择一次受控复制来隔离慢消费者。录音或ASR不能长期占用实时收发池。稳态热路径以无通用堆分配为目标，必须用测量验证，包括第三方库；池耗尽不允许无限扩容。

首期媒体图采用有限模板，在会话建立时验证节点、准备缓冲和执行顺序。已发布的 G.711 图包含双腿桥接与本地 A 腿两种独立模板，固定原生8kHz、单声道、20ms；双腿可以实际解码并在PCMU／PCMA之间转换，本地模板支持提示音、按键发送和有界PCM下行。该模式须显式启用并通过当前Worker能力校验，主服务采用relay时不会自动执行此图。见双腿媒体合同和本地媒体合同。

1.13 候选将本地 A 腿实际观察经独立 FD4 RXS2 送到 Go SDK，保持原生 8kHz、20ms，并区分真实解码、历史 PLC、CN、缺口和来源边界；Server 只在实际 ACK、本地分配、同代健康及能力核验后授权。RX 不占用 TX 互斥，可与 PCM 下行并行。真实 SIP 与进程暂停试验已限定通过；实际安装版本须另核 GET /v1/docs 及部署回执，详见RX 收音合同。

任意图变更、外部流式 ASR、VAD、双轨录音、G.722／Opus 实时处理及分支重采样仍待补齐；内部收音基础与离线 SDK 不授予这些运行能力。后续图变更必须在明确帧边界切换版本，热路径不查询动态配置、不解释脚本、不加载文件。

对话时间线与有界背压

每轮TTS必须带turn_id或单调生成版本。已发布的PCM轮次具备严格递增turn_id、旧轮音频拒绝、原子替换和发送前版本复查；真实供应商取消尚待接入。后续取消上游不能成为本地停播的等待条件。1.12 本地 PCM 与入站 A 腿解码消费独立，不回灌为回声；1.13 候选增加独立上行 SDK，但仍未向外部 ASR 持续交付。ASR默认读取对端接收轨，不能混入自身TTS；回声与误打断单独测试。

当前PCM中断允许0／20／40ms：0立即清除待发音频，20／40ms仅对已经排队的至多1／2帧淡出，不等待新音频或复制最后已发帧；重复淡出不会延长旧轮播放。PCM和主动DTMF共用本地TX身份，连续音频保持20ms／160ticks时间线。uuid_break、read终止键和VAD不会自动映射为PCM中断，业务须明确调用INTERRUPT。完整边界见内部PCM轮次、私有RVA1入口和v1.12验证。

1.13 候选的普通 RX 观察携带从 Graph 原始观察开始、不可续期的 100ms 期限，覆盖 Rust 队列、OS socket 和 Go SDK 停留。接收、Read、Server 交付分别复查；到期、时钟不符、慢消费均显式失败，不能当成静音。挂机先撤读权再等待真实释放，未知控制结果保留同一清理句柄；同 ID 缓存回执不复活旧流。调用方在真正使用音频前仍须复查期限，函数检查点与后续供应商写入不是原子保证。

完整智能体仍需分别记录用户开始讲话、确认打断、媒体开始停旧音频、最后旧包提交，以及回复已生成／已接收／已发送进度；当前样本和轮次计数不等同这些端到端时延已经验收。无法取消已进入网络和终端缓冲的数据，不承诺远端立即静音。

队列 满载行为与必需观测
实时RTP／PCM 有界条数／字节／时间，记录内部丢帧与超时，触发准入保护
ASR上行 1.13 候选内部 Graph、Rust 导出与 Go SDK 各有独立 8 槽边界，另有摘要和 OS 缓冲；过期或慢消费显式缺口/失败。外部适配器仍须设置自身上限和恢复策略
TTS下行 限制超前生成和接收，取消后续生成；不任意掐掉一句话中间音频
录音 专用有界缓冲、异步写入；失败显式报告，必需录音故障按业务策略决定继续或挂机
日志诊断 限量采样，默认不逐包记录，不能阻塞通话

所有队列需暴露长度、字节量和最老数据年龄；音频队列同时以毫秒计预算。按线路设置抖动缓冲最小／目标／最大值。丢包、静音、DTX、CN与PLC保持可区分；FEC恢复和额外等待单独权衡。保护观察最忙Worker、发送迟到、池水位和队列年龄，优先拒绝新呼叫保护存量。

三类压测与可靠性验收

分别报告纯转发、编解码、完整Voice Agent链路。主验收包含真实非静音音频、电话Codec、流式ASR/TTS、VAD、打断及双轨录音。先用可控模拟供应商保留真实协议与连接成本，再接真实供应商，不用无连接的空函数代替。

固定硬件、资源配额、CPU/网卡/内核、Codec、ptime、时长分布、加密、录音及网络条件；基线采用合理调优的FreeSWITCH并计入所有辅助进程。报告CPU、RSS、PPS、Worker负载、队列年龄、池水位、内部丢帧、发送迟到、录音完整性及ASR效果。

故障集包含集中建呼／挂机、突发TTS、ASR停止读、慢磁盘、网络乱序／丢包、控制面断连、重复命令、畸形协议、端口复用与FFI错误。声音覆盖连续语音、双方抢话、短回答、长回复、频繁打断、长通话及采样率变化。原生库、模型或录音故障不能无界拖慢其他分片。

网络后端先用非阻塞UDP与就绪循环。recvmmsg/sendmmsg每次作用于一个socket，独立RTP端口下的批处理收益需实测；不等待凑批或突发发送几百毫秒音频。共享端口必须证明线路兼容和正确分流。io_uring为可替换后端；AF_XDP/DPDK仅在分析确认瓶颈后评估。

容量规划同时估算网络和磁盘：20ms连续媒体每单向流50包/秒，单腿双向万路约100万包/秒，双腿桥接约200万包/秒，额外RTCP和AI通信另计。双轨16k/16-bit PCM约64kB/s/通话，万路约640MB/s、2.3TB/小时；这些是格式算术，不是容量实测。

推进顺序与交付

阶段 重点 通过条件
0 现网基线 固定等价配置并解释CPU／线程／网络／录音瓶颈
1 单Worker媒体闭环 G.711、播放、时间线、基础缓冲，正确性和单核测量可复现
2 AI闭环 ASR／TTS、全双工、版本打断、双轨录音，质量与异常测试通过
3 多核与容量 分片、NUMA、网络I/O和准入，目标并发与尾延迟联合达标

升级默认新呼叫切流、旧呼叫排空；首期不承诺活动媒体无损迁移。控制接口需幂等、事件序号、会话版本和断连后同步，现有局部能力必须在完整链路中复验。

交付包含模块／接口契约、线路互通清单、可复现压测脚本、容量报告、部署调优和故障回滚手册。优先顺序为音频正确稳定、单核效率、多核扩展、内存复制优化、进一步网络后端。
