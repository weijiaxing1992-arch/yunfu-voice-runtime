实时 G.711 双向媒体处理说明

v1.10 当前 build-03 / processed-03 的 11 场景×两种 UDP 模式共 22/22 通过，独立发送方暂停恢复用例 4/4 通过。历史 build-02 管理实测三项单路与 100 路通过、500 路失败；当前testlab-02三单路及100路通过、500路仍失败。见本轮发布复核与管理测试摘要。结果来自隔离候选，运行后台版本以 GET /v1/docs 的 version 字段核对；5000/10000 路处理容量与完整 Voice Agent 未完成。

本文双腿合同在 1.12.0 保持；新增本地 PCM 轮次与已 ACK 外部下行见 本地处理、内部 PCM、RVA1 和 1.12 验证。新增结果不重标本页历史容量失败。

M1 增加显式启用的双向 G.711 处理图：每个方向先对编码 RTP 包做有界重排，再解码成 PCM，编码成目标腿的 G.711 格式，最后使用本机 RTP 身份重新封装。A、B 两腿可以分别使用 PCMU 和 PCMA；即使两腿编码相同，启用该模式也会真正执行解码和编码。

1. 启用方式与适用呼叫

在独立实例的完整启动配置中，将 media.processing 设为 g711。以下是配置片段，需要合并到已有完整配置：

{
  "media": {
    "processing": "g711"
  }
}
配置值 行为
字段省略或空字符串 保持既有 relay 透传模式
relay 显式使用既有透传模式
g711 对该实例符合条件的双腿呼叫启用 M1 处理图
其他字符串 配置校验失败，不能静默回退

这是启动配置，不是逐呼叫的 ESL 变量，也没有在途图迁移或热切换功能。建议先在独立 SIP、媒体和管理端口的实例验证；实际启用前，应完成配置检查和有序排空。配置校验命令为：

./bin/rustswitch -config config/processed.json -check-config

示例文件名表示使用者准备的完整配置文件。media.binary 必须指向与控制面匹配、声明处理能力的新 Rust 媒体二进制。校验成功只证明配置可接受，不能替代启动握手、实际通话和容量验证。

本页原 22 项验收专用于经固定上游建立 B 腿的双腿 SIP 通话。v1.10 在 g711 模式拒绝本地自动应答/IVR；v1.11 增加 topology=local 的独立单腿实现与验收集合，v1.12 在该拓扑增加有界 PCM 下行，见本地合同。旧双腿通过不能授予新本地功能通过，也不表示全部 IVR 已兼容。

2. 媒体与协商范围

项目 M1 当前合同
主音频 PCMU、PCMA，即 G.711 μ-law / A-law
采样率与声道 8000 Hz、单声道
分包时长 固定 20ms；每包必须恰好 160 字节 G.711 负载
A 腿 PT 保留 A 腿有效的静态或动态映射；编码由协商元数据确定
B 腿报价 实际提供静态 PT 0 的 PCMU 和 PT 8 的 PCMA
B 腿应答 只能选择已报价的 PT 0/PCMU 或 PT 8/PCMA；任意动态改映射不接受
电话事件 已协商的动态 telephone-event PT、8000 Hz 时钟、双方认可的事件集合
舒适噪声 已协商 CN、8000 Hz 时钟；保留 SID 语义，不合成噪声 PCM
传输 固定 IPv4 UDP 媒体对端，RTP 与 RTCP 使用独立端口
图方向 A 输入→B 输出，B 输入→A 输出，分别持有 RX、缓冲、codec 和 TX 状态

同一通话两腿可以采用 PCMU→PCMA 和 PCMA→PCMU 的相反转换。A 腿使用动态 PCMA PT 时，不会把该动态 PT 当作 B 腿已报价的格式，也不会错误地用 A 腿 PT 检查 B 腿输入。

ptime=20 同时由 SDP 选择与实际 RTP 负载长度检查约束。实时 codec 库中存在其他帧长的缓冲 API，不表示 M1 通话图已经支持 10/30/40/50/60ms。

早期 183 应答可缩小辅助负载集合，最终 200 可在原始报价范围内恢复 telephone-event/CN。恢复只更新辅助协商，不重启已经运行的主音频图。连接后主 codec、主 PT 和 B 腿媒体地址不能任意改变；这不是通用 re-INVITE、UPDATE 或网络迁移实现。

3. 内部 PCM 与执行模型

实际路径如下：

协商来源的 RTP
  → 借用报文视图与格式检查
  → 单方向 RX 状态 / 编码包重排
  → G.711 解码
  → 8000 Hz、mono、i16 的借用 AudioFrameView
  → 目标 G.711 编码
  → 本机 SSRC / 包序 / RTP 时间戳封装
  → 对端 UDP

M1 桥内 PCM 当前是原生 8k 单声道，尚未在通话中统一重采样成 16k。已有离线音频 SDK 的可变采样率能力和 C ABI 属于另一层接口，不能据此宣称实时 ASR/TTS 分支已接入。

PCM 帧携带媒体位置、真实输入 RTP 时钟位置和来源标记，区分实际解码与历史补偿。处理图使用 worker 事件循环与调用方缓冲，建呼时准备固定资源；不为每个呼叫创建音频线程。编码包缓冲不在每个 RTP push/pop 时分配内存。

协商 telephone-event 时，每个方向还会在协商阶段分配固定的 DTMF 时间戳映射历史：256 项，当前已检查构建的状态大小为 4136 字节/方向。逐包处理复用这些状态；没有协商按键的方向不承担这项分配。该结果不能推广成“全产品每帧零分配”或“建呼/重新协商完全不分配”。历史按源和展开的 RTP 起点区分，旧结束副本沿用原输出起点；已经被有界历史淘汰、无法确定旧映射的事件不能套用新段偏移猜测转发。

4. 抖动、静默和时间戳

当前处理计划固定目标延迟 40ms、最大延迟/无输入补偿预算 120ms。每个方向使用 8 个固定编码包槽，音频和辅助包共同占用；每槽负载上限 480 字节，实际主音频仍限定 160 字节。底层通用缓冲可配置时钟和 packet ticks，最大 16 槽，但这些内部参数不是本次开放的管理页调优选项。

音频缺失按主音频时间戳位置判断，不能按包含 DTMF/CN 的 RTP 包序空洞推算。重复、乱序、已迟到、容量溢出、格式拒绝和本机播放过期分别计量。RX 分别展开 16 位包序和 32 位时间戳；更换 SSRC、明显序号跳变或时间戳重启需要确认，随后清除旧源播放历史。

有历史时，G.711 采用有限历史衰减补偿，最多 120ms。它不是 G.711 附录 PLC 的等价实现，也没有完成 MOS/PESQ 等音质等价验收。没有历史或补偿预算耗尽时返回缺失，不用零填充伪造“真实静音”。连续没有实际音频输入时，最多产生 6 个 20ms 缺失位置，之后暂停无输入音频定时工作。

已经收到的 CN/DTMF 可提前抑制其覆盖位置的假缺失，避免辅助包与音频期限相差几百微秒时额外产生 PLC。真实音频优先。时间戳不晚于已播放语音、或已被同位置排队语音覆盖的 CN，在出队时直接丢弃，不能继续清除新语音的补偿历史或向下游发送旧 SID。

明确静默后的新语音段可以使用不同于旧段的时间戳相位。新段边界随实际播放帧传递，首帧过期也不会丢失边界；媒体图在消费边界时保证输出 RTP 与 PCM 位置不回退。当前活跃语音段仍检查固定帧相位，不把每个异常时间戳都当作合法重启。

本机调度过期与远端静默分开处理。worker 被暂停或抢占后，仍使用原期限判断内核积压包，过期包丢弃；不能将这些包重新排到“到达时间加 40ms”，否则旧声音会被延后重放。确定性修订对照已确认：381ms 恢复时，下一个有效帧继续使用原 400ms 期限，修复前曾被改排到 421ms。

DTMF 活动状态只保留最新事件起点；迟到的旧结束副本不能覆盖较新事件。相同起点的多事件块分别保存 0–16 已支持事件的持续时间与结束位，时长只增、结束位不回退。旧重复包不会不断刷新活动超时；超时后保留有界状态，只有未结束事件的真实进度可重新开始等待。

5. 发送期限与 RTCP

音频或辅助报文落后计划期限达到一个 20ms 帧时，不集中补发。worker 在每个调度项与真正发送前重新读取单调时钟；编码后再遇到调度暂停，也必须执行发送前期限检查。UDP WouldBlock 或其他发送错误采用即时失败/丢弃策略，不排无界重试队列。

RTP 序号在准备报文时消耗，发送失败后不能把同一个序号复用于不同内容。收发成功计数表示本机系统调用接受的数据，不能证明终端实际收包、网卡零丢包或最终可听音质。

处理模式终结 RTCP，使用本机 TX SSRC 生成报告；已经发过 RTP 时发送 SR，否则发送 RR，并带 SDES CNAME，释放时尝试发送一次复合 BYE。接收统计来自对应腿的 RX，不能将原端点的报告原样转发后称为本机生成。

SR 媒体时钟与最后一个网络包的时间戳分开保存，恒定起点的DTMF结束副本、迟到CN与普通发送抖动均不能倒推已外推的SR时钟；原RTP包仍保留其采样起点。RR 丢失统计覆盖实际 RTP 包序，包含辅助包，与音频缺失位置计数不同；主音频 jitter 按到达顺序估算。LSR/DLSR 使用真实收到的已知源 SR 和单调经过时间。

当前报告周期在 2.5–7.499 秒范围内分散，尚未实现完整 RTCP 带宽自适应调度。复合输入校验有 2048 字节、32 子包上限，先完整校验再更新状态；解释 SR/RR/SDES/BYE，其他有效类型按长度跳过。不提供 rtcp-mux、SRTCP、扩展反馈拥塞控制或 FreeSWITCH 同名 RTCP 事件的完整行为。

6. Go / Rust 内部接口

M1 沿用逐行 JSON 内部协议，协议主版本仍为 1。它不是 ESL 命令格式，也不是 FreeSWITCH 原生模块 ABI。启动 ready 回执必须包含精确能力名：

{
  "id": 0,
  "ok": true,
  "type": "ready",
  "protocol_version": 1,
  "worker_id": 0,
  "pid": 12345,
  "capabilities": ["processed_g711_v1"]
}

示例 PID 仅展示字段。Go 使用 g711 模式时，旧 worker 缺少该能力会被拒绝，不能作为健康处理分片接纳呼叫。allocate.processing 必须是以下完整计划：

{
  "version": 1,
  "mode": "g711",
  "jitter_target_ms": 40,
  "max_delay_ms": 120
}

完整分配请求示例，地址仅供隔离本地 fixture 使用：

{
  "id": 1,
  "op": "allocate",
  "session": 42,
  "a": {"rtp": "127.0.0.1:41400", "rtcp": "127.0.0.1:41401"},
  "payload": 0,
  "codec": {"name": "PCMU", "sample_rate": 8000, "rtp_clock_rate": 8000, "channels": 1, "ptime_ms": 20, "fmtp": ""},
  "dtmf_payload": 101,
  "dtmf_clock_rate": 8000,
  "dtmf_events": "0-15",
  "cn_payload": 13,
  "cn_clock_rate": 8000,
  "processing": {"version": 1, "mode": "g711", "jitter_target_ms": 40, "max_delay_ms": 120}
}
请求/回执 关键要求
allocate 相同 session 与全部参数的重复请求返回同一分配；计划不匹配必须失败
allocated 实际创建处理状态才返回 processing_version: 1，并包含 session 与 A/B RTP/RTCP 四端口
旧 allocated 未请求处理时省略处理版本；请求处理却没有版本，不得当作成功
connect 提交 B 腿真实协商 peer、payload、codec、DTMF/CN；不再次携带或更改 processing 计划
release 不存在 session 也确认；释放图、定时状态及端口，端口仍经过复用隔离
stats 返回真实处理计数；Go 校验必须字段、整数、帧/样本一致性和延迟桶形状

所有命令回执携带对应的 id 与 ok。处理分配成功示例：

{
  "id": 1,
  "ok": true,
  "type": "allocated",
  "processing_version": 1,
  "session": 42,
  "a_rtp": 30000,
  "a_rtcp": 30001,
  "b_rtp": 30002,
  "b_rtcp": 30003
}

端口必须取实际回执，不能沿用示例值或推测每个请求都能获得同一块。

建呼阶段的 allocated 只证明资源和处理状态已建立，不代表已经接通、已经执行 codec 或远端收到媒体。业务判断应继续结合 SIP 应答/ACK、处理帧计数与真实对端收包。

7. 故障行为

情形 当前处理
非 G.711、非 20ms 或不支持的 SDP 拒绝，不隐式回退到 relay
本地 IVR/XML 本地路由使用 g711 模式 v1.10 返回 488；当前须具备本地能力及正确 local 分配回执，独立验证
B 腿选择未报价的格式/映射 488 Incompatible SDP Answer
worker 能力缺失或分配版本不符 启动/媒体 RPC 失败，不能报告处理成功
媒体资源无法分配 呼叫清理并返回媒体分配错误；不占住失效通道等待
音频负载长度错误、未协商辅助 PT/事件 计入拒绝/格式指标，不送入 codec
缓冲满、旧包或本机期限过期 分别计数并丢弃，后续媒体继续有界推进
发送失败 不无限等待，不复用已消耗序号，区分网络系统调用失败与发送前期限错失
来源重启、合法 BYE 或通话释放 重置相应状态或释放资源；旧来源不能通过旧端口/队列污染新会话

8. 可观测指标

JSON 入口为 GET /v1/status 的 workers[].stats。标量同时以 rustswitch_media_<字段名>{worker="…",generation="…"} 出现在 /metrics；当前数组桶通过 JSON 获取，不能把它当作已经发布的 Prometheus histogram。

字段 单位和语义
processed_active_calls 当前实际拥有处理图的媒体会话数；不是 SIP 已接通数
processed_decoded_frames / processed_decoded_samples 实际解码的主音频帧/样本；不含 CN、DTMF 和缺失
processed_encoded_frames / processed_encoded_samples 实际编码帧/样本，可包含历史补偿；不等于对端收到的帧
processed_plc_frames 有限历史补偿产生 PCM 的次数
processed_missing_frames 无历史或预算耗尽等情况下没有 PCM 的缺失次数
processed_cn_packets 交给处理图的合法CN次数；不表示UDP提交成功，过时SID不增加它
processed_jitter_lost 到期而没有真实音频的主音频位置，包含没有 CN 时停止输入后每腿最多 6 格尾部补偿；不能称为实际网络丢包数
processed_jitter_late 已迟到的输入，包含被新语音覆盖的旧 CN
processed_jitter_reordered RX 接受到的重排包
processed_jitter_duplicates 重复包或重复音频时间位置
processed_jitter_overflow 槽容量或允许的未来排程范围超限
processed_playout_expired 本机调度已跳过的音频时间位置
processed_aux_expired 辅助期限过期、被语音覆盖的CN，或无法恢复时间映射的旧DTMF
processed_aux_timeouts 未结束事件的有限活动等待超时
processed_queue_reset_drops 辅助重新协商剔除、确认媒体源重启和远端 RTCP BYE 造成的排队包清理；普通时间线重锚不清队列。此指标不统计通话 Release 销毁的待消费尾包，历史累计也不因通话释放而清零
processed_source_resets 经确认的源/序号/时间戳重启
processed_send_errors 实时 RTP/RTCP 的本地发送或构造失败；不含独立记录的发送前期限错失
processed_send_deadline_misses 实时发送期限违例；原桥接发送前迟到至少 20ms 拒发。1.12 PCM 另包含编码前超期及 UDP 已成功返回但相对计划已迟到至少 20ms，实际已发送量仍保留
processed_output_lateness_ns_max 最终发送前（或编码前已确定超期）检查相对计划的最大迟到，单位纳秒；不包含 UDP 调用返回耗时
processed_output_lateness_buckets 同一发送前检查口径的 8 个非累计区间，包含期限拒发尝试；PCM send_return_late 可使 miss 非零但对应发送前桶仍低于 20ms

延迟桶按顺序为：≤250µs、(250µs,500µs]、(500µs,1ms]、(1ms,2ms]、(2ms,5ms]、(5ms,10ms]、(10ms,20ms]、>20ms。它们不是累计 le 桶，也不是端到端口耳延迟或精确 P99；使用者应据真实计数给出分位数所在区间。

本模式满足 decoded_samples = decoded_frames × 160、encoded_samples = encoded_frames × 160。所有累计值按 worker 进程代次解释，重启后归零；跨代次求和时需保留 generation，不能把重启后的零解释为“此前没有故障”。

排查时应同时查看既有 rx_packets、tx_packets、source_rejected、invalid_packets、rate_limited、send_errors、内核接收丢包、CPU、内存和准入原因。不要只看 active_calls 就认定媒体已通。

启动时尚未取得第一份完整 worker stats，数据应显示为未知；缺字段不能补成零。testlab-01 的五项作业各保留一次 status_sampling_errors=1，诊断是 worker 统计字段尚不可用，随后才获得实际样本。该字段同时记录 HTTP 读取失败和响应统计校验失败，因此不能把这五次诊断写成“五次 HTTP 断连”。当前testlab-02外层411次/总采集412次读取错误也为零，五项作业各有一次启动未知统计，详细口径见发布复核。运行中持续缺统计、代次变化或 HTTP 超时仍须分别排查，不能沿用旧零值。 对失败作业还需区分HTTP读取时刻与worker实际采样时刻：testlab-02的500路最后响应携带发生器退出前的缓存，不能以该帧总数认定完整结束或释放后归零；进程/端口清理由独立证据确认。

11. 管理集成与继续工作边界

v1.10 候选已将 GET /v1/codecs 接入有效配置及当前 worker 能力：media_mode=g711_audio_graph、runtime_media.processing=g711，所有预期 worker 当前代次均健康且具有 processed_g711_v1 时才报告 live_transcoding=true。live_codec_profiles 在本模式限定 PT 0/PCMU 与 PT 8/PCMA。native_audio 和 native_probe_error 继续单独报告离线 SDK 探测结果。这个目录证明配置与握手就绪，不证明实际通话或容量已经验收。

管理压力/小电话请求的 media_processing 显式选择独立测试实例模式，省略或空值规范为 relay；不会继承或修改主服务模式。g711 只允许 G.711 预设，并使两腿选择相反编码。已实际验证在 relay 外层管理实例发起 G.711 测试，也验证在 G.711 外层显式发起 relay 测试。请求受理、实例就绪和全部媒体验收是不同阶段。

处理发生器 g711-pcm-v1 使用独立 G.711 解码校验实际载荷，160 个样本全部检查。测试波形采用 16 个间隔 2048 的 PCM 电平，前部还携带流、方向和帧位置；每个目标样本与来源律解码参考值的绝对误差必须不超过 512 个有符号 16 位 PCM 幅度单位。512 是这组已知电平跨律有损量化的固定门槛，不是 512 字节、512ms、任意语音质量标准或允许 512 个错包。只改 PT、串流、固定静音、序号/时间戳错误与超期均不能靠量化容差通过。

接收端还独立检查新 SSRC、方向、连续序号、时间位置、内容唯一数和有限 PLC 尾帧。正常输入结束后每方向最多 6 帧尾部补偿单列，不计入有效源音频，也不冲抵丢包。发生器的观测窗口与网络到达诊断不改变 Rust 发送前的实时期限。这些结果在旧 build-02 管理测试中表现为100路通过、500路失败；当前build-03复测也仅三单路及100路通过，500路有效唯一内容1,498,372/1,500,000，时间戳错误0，仍有988内容异常、499过密到达、2序号异常和3306发生器迟发，整体失败。

发生器的 processed_diagnostics 是有界归因附录：内容有效但时间轴错误的包仍不合格，首错原包与写入前后时刻可辅助区分输入迟发和接收失败。每方向首错，接收首错与迟写列表各最多32条；不改变发送/接收期限和有效源音频计数。

本次尚未完成 G.722/Opus/G.729 等实时图、实时重采样与 16k AI 分支、ASR/VAD/TTS 服务接入、双腿处理桥的播放混入及 DTMF 注入、WebRTC/ICE/DTLS-SRTP、SRTCP/rtcp-mux、完整 FreeSWITCH 模块 ABI 和所有媒体控制入口。

单向 20ms 为 50 音频包/秒，双向每呼叫为 100 个输入主音频包/秒。5000 路意味着约 50 万输入主音频包/秒，并有相应输出、辅助包、RTCP、SIP 与业务工作量；这只是负载定义，不是已达到的性能数字。旧 relay 容量或离线 codec 吞吐不能推算为 M1 的 5000/10000 路承诺。
