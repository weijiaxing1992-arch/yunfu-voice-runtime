暂停恢复修复与容量复测

新增真实网络用例在同一 SSRC、连续来源序号和 160 ticks 相位下，让发送方从 1.2 秒停顿到 1.383 秒，再恢复原发送计划。旧 build-02 的 PCMU、PCMA 两个普通 UDP 用例均实际失败：恢复后输出时间戳持续偏离原采样格点。失败日志和原帧保留在 recovery-before-01 及 recovery-before-01-summary.json。

build-03 修复 Graph 将同源、同采样相位的恢复误按墙钟重新定位的问题；实际发送媒体已越过来源位置或真正改变采样相位时，仍保留防止倒退的边界处理。recovery-after-01 两种 UDP 模式共 4 项通过：恢复后的真实音频内容和时间位置完整，对向持续输入不受影响，源重启和发送错误为零，真实晚到输入仍按原门槛计数。它是新增独立集合，不合并到原 22 项中重复计数，也不等于 500 路已成功。

发生器新增有界 processed_diagnostics，分别记录内容本身有效但时间戳错误的包、首错原包及 UDP 写入前后时刻。每方向仅保留首错；接收首错与迟写两个汇总列表各最多 32 条，实际 UDP 受理只说明本地提交；诊断计数不增加合格接收数、不抵消 missing、不降低 PCM 或时间线门槛。

当前 500 路复测仍失败

testlab-02/03-relay/g711-pressure-500-report.json 实际接通500路、持续30秒，完整发送1,500,000包。有效源内容唯一数为1,498,372，未获得合格唯一内容的位置为1,628；收到的媒体包总数1,505,360含6,000尾部PLC。timestamp_errors=0，但仍有988次内容不匹配、499次过密到达、2次序号错误和3,306个发生器迟发包，故整体仍失败。这些计数存在重叠，不能相加解释为真实网络丢包。

有界诊断记录全部1000个发送方向出现迟发，保留的最早一批计划时间约22.31秒；最长写入调用约3.194ms，最迟写入返回相对计划约48.491ms。write_attempt_late_packets=3306、write_return_late_packets=3310 分别按调用前后边界计数，不能把本地UDP返回当作远端已收到。它们支持继续调查该时间段的共同调度停顿，尚不能独立确定是GC、操作系统调度或其他原因。

独立复核在一次约1秒的worker采样窗口观察到late/lost各1074、过期552、无PCM缺失86、PLC988及发送前期限错失2，随后约7秒同类计数未再增加。数值之间的对应仅为累计统计关联，不能视为逐包证明。500路失败路径的最后HTTP读取发生在发生器退出之后，但它携带的worker缓存采样更早；这份缓存不能充当完整结束帧数或释放后会话数的验收证据。隔离进程和端口的正常清理另有直接检查。

与旧testlab-01相比，时间戳异常从443,207降为0，证明本次记录未再出现持续的错误时间轴；这不会消除仍存在的内容、期限和序号问题。三项单路及100路本轮再次通过，500路保持失败状态，继续采用原质量门槛定位和复测。

历史 500 路失败必须保留

testlab-01/03-relay/g711-pressure-500-report.json 的原结果为失败。发生器记录实际收到 1,505,776 个媒体包，其中有效源内容唯一数为 1,054,811；同时记录 443,207 次时间戳异常、10,968 次内容不匹配、530 次过密到达和 9,595 个发生器迟发包。这些指标可能重叠，不能相加解释成网络丢包总数，也不能用总收到包数掩盖内容/时间位置错误。

媒体快照记录实际解码 1,487,890 帧、编码 1,491,904 帧，另外有迟到、过期和有限补偿统计。这份历史记录足以判定当次验收未通过。随后已用独立复现确认并修复同源暂停恢复的时间轴缺陷，但不能据此推断历史所有异常均来自单一原因；testlab-02 已按相同内容和期限门槛复测，时间戳异常为0，但其他严格条件仍未通过，不能宣称500路成功。

该次测试在本机 Apple M4、10 个物理/逻辑 CPU、16GiB 内存的 Darwin/arm64 桌面环境运行，宿主还有常规后台应用；环境记录为 review/host-environment.json。portable UDP 发生器包含 8 个发送 worker、64 个接收 worker 和隔离的测试服务。这不是 Linux 专用硬件验收。各外层隔离实例均有序退出、端口释放，主服务配置与活动计数保持原状态；正常回收不等于媒体验收通过。

管理可用性和未知统计

当前 testlab-02 三组外层实例的实时观察记录合计 411 次 HTTP 读取，读取错误为 0；原总摘要另记录 412 次 sampling_read_attempts，错误为 0，其中包含总采集范围的额外读取。两种口径分别保留，不混作同一计数。外层记录的最长三接口读取组约8.914ms，总摘要最长单次读取约7.585ms；这不是 P99、SLA 或高负载长期可用性证明。

当前五项作业仍各出现一次 status_sampling_errors=1，保留的诊断字段为 active_calls、tx_packets 或 peak_resident_bytes。旧testlab-01同为外层411次/总计412次读取均无错误，最长读取组9.095ms、单次13.057ms及旧未知字段记录完整保留在历史摘要，不能混用两轮延迟。它们是启动阶段第一次完整统计之前的“未知”，外层 HTTP 请求没有因此失败。字段缺失不得补零；第一份有效样本到达后才用于图、趋势和峰值。

当前 status_sampling_errors 同时包含 HTTP 读取错误和响应内容校验错误，必须结合 last_status_sampling_error、采样阶段和原 HTTP 读取记录解释。运行中持续缺字段、HTTP 超时或 worker 代次改变也不能套用“启动未知”说明后忽略。500 路此次媒体失败与启动时的一次未知统计分别记录。

量化校验没有降低业务要求

处理发生器的 g711-pcm-v1 校验全部 160 个样本，而不是只检查 RTP 头或 PT。固定测试电平相隔 2048 个 PCM 幅度单位；每个目标样本相对来源律实际解码参考值的绝对误差必须不超过 512 个 signed 16-bit PCM 幅度单位。它覆盖这组已知电平的 PCMU/PCMA 跨律有损量化，不能接受相邻错误电平、串流或固定静音。

512 不是允许的错包数量、字节数或时间；这也不等价于任意真实语音的音质/MOS 标准。独立 M1 波形测试另保留自身的逐帧内容断言，两套测试不可互相冒充。辅助媒体、原生码字、有效源音频和有限 PLC 分别计数；尾部补偿不能填平源包缺失。

Rust 仍按原计划期限播放：晚到一个 20ms 帧的内容不集中补发。发生器的本地到达观察窗口不改变生产发送期限。旧 worker 暂停恢复导致约 50ms 持续额外延迟的失败证据，以及旧迟到 DTMF/CN 问题的修复前后证据均继续保留。

历史证据与本轮新增

work/voice-runtime-m1/processed-final-02.receipt.json 属于此前源码。导入器可完整重放原报文，但功能代码或测试改变后应保持 stale；没有把旧源码清单补写成新构建来源。

本轮 processed-01 的 UDP 模式 11 项通过，connected 模式有一项发生器未生成完整输入而失败。原循环在短尾期到达时提前退出；修复后仍受原 50ms 发生器迟到上限约束，没有放宽媒体的 20ms 过期期限。重新构建后 processed-02 才取得两种模式各 11 项成功。

当前冻结源码的固定原版 26 探针已重新运行，位于 work/linux-vm/share/voice-runtime-m1-recovery/paired-01.json，成对指纹为 ec95383ddfb8c2e257d585bea1963742ea5b643adc2fbfc4211188c510b0eed6。正式成对 JSON 已更新，运行后台实际版本以 GET /v1/docs 的 version 字段核对；旧 voice-runtime-m1-next/paired-01.json 保留为历史。其独立成对指纹仅涵盖该执行器定义的功能范围。原版安装、配置、模块与证书的 243 个文件在运行前后匹配冻结清单，原版与候选均已清理，隔离 VM 正常关机。这个范围和 M1 完整运行快照不同，不能由其中一个指纹推出另一套测试已执行。

M1 与 M2 的剩余工作

M1 当前限双腿 G.711、8k 单声道、20ms、固定 40/120ms 缓冲与已协商 DTMF/CN、基础 RTCP。发送方暂停恢复缺陷已按独立用例修复，本轮完整500路复测仍未通过；仍需按同等硬件、全部辅助进程资源和音质/尾延迟标准完成更高并发、长时间稳定性及原版性能对照。G.722/Opus/G.729 实时图、其他帧长、重采样、处理图本地 IVR/播放混入及按键主动注入仍未完成。

M2 的真实流式 ASR、TTS、VAD、Turn 取消与迟到音频失效、实时双轨录音和有界背压尚未接入完整通话链路。现有 AudioFrame SDK、有限 tone/WAV 播放和事件 journal 不等于完整 Voice Agent。WebRTC/ICE/DTLS-SRTP、完整 SRTCP/rtcp-mux、通用原版模块宿主也不在当前已验证范围。

研发继续优先实际电话链路和 Voice Agent 接入。相对优化后 FreeSWITCH 的 1.5 倍性能、资源下降目标、72 小时混合负载与生产无感替换仍是待测目标。
