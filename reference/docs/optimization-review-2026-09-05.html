RustSwitch 代码与容量优化审查

历史审查记录：以下复现描述审查时的 0.2 原型，不表示当前缺陷状态。文档 1.2 对应实现已修复 Go 媒体提交乱序、连续早期媒体更新积压及异常释放处理，并补上管理和媒体资源预算。最新行为、保护边界见稳定性说明。原版动态差分、控制重启无损保持通话及 Linux 万路认证仍未完成；历史源代码行号只用于当时复现，不作为当前实现定位。

审查日期：2026-09-05。对象：当前 0.2 原型。目标保持为 Rust 媒体核心、Go 控制面、C/C++ 生态适配、单机一万通话及 FreeSWITCH 无感替换。

最先要修复的是媒体配置命令乱序：当前代码可以先执行最终接通配置，再被旧的早期媒体配置覆盖。本轮已在源码副本中复现。随后应处理控制故障扩大、端口准入及异常清理，再完善真实持续负载验收和媒体性能。

本轮审查主要覆盖媒体循环、控制 RPC、SIP 状态处理、定时器、日志及压测工具。没有修改交付目录中的运行代码，也没有重新执行万路压测。最终千路 60 秒完整收发 5,999,904 包是既有测量；万路媒体与 Linux 容量仍未通过，见原性能记录。

1. 同会话媒体命令乱序：优先修复

**触发：**上游先发携带地址 X 的 183，紧接着发携带地址 Y 的 200。控制面为两个媒体连接命令分别启动 goroutine，实际入队顺序没有保证。

证据：submit 独立启动 goroutine；connect 只在控制结果中保留 ConnectVersion；Rust Connect 没有会话变更版本。旧回复过滤 发生在命令执行之后，无法撤销已发生的媒体修改。

副本测试设置 GOMAXPROCS=1，使用实际 Go 提交和 Pool 代码、模拟媒体协议进程，连续 3 次观察到：

worker_seq=1  connect_answer  version=2  B=127.0.0.1:20004  DTMF=nil
worker_seq=2  connect_early   version=1  B=127.0.0.1:20002  DTMF=101

这是命令执行顺序的复现，未声称已经做过该场景的 Linux 实际音频测量。实际 Rust 执行层会按到达顺序更新 call.b 和 call.dtmf，因此存在接通后无声或单向音的风险。

**建议：**同会话的 allocate/connect/release 通过有序调度器提交；请求携带会话变更版本，Rust 执行前拒绝旧版本。重复同版本请求必须核对参数；已释放会话不能被迟到 connect 恢复。不要仅依赖 Go 内存竞争检测，这属于执行顺序错误。

**验收：**不同地址和 DTMF 的 183/200 连续到达、重复与延迟回复、CANCEL/BYE 穿插等情况下，最终媒体配置始终与最新有效状态一致。

2. 控制请求超时与媒体失效应分开处理

pool.go 为每次 RPC 设置 1 秒定时器，超时直接终止进程；每秒 stats 也使用同一逻辑。进程退出后，workerFailed 结束所属通话。

本轮使用协议模拟进程，将只读 stats 回复延迟到 1.2 秒，观察到进程被终止。启动后约 2 秒出现失败，因为先等待约 1 秒的统计周期，再达到 1 秒 RPC 超时。这证明当前监管行为，不代表已测出 Linux 上出现此延迟的频率。

**建议：**只读查询超时先暂停该分片的新准入并标记统计过期；进程失效由独立存活检查和媒体循环进展共同判断。引入有界在途请求表、迟到回复处理及操作状态查询。变更请求超时必须区分“未执行”和“执行结果未知”，再决定重试或对账。只加长超时时间不能解决故障隔离问题。

更长期的限制是 Go 进程退出会关闭管道，Rust 命令通道断开 或回复写入失败 就退出。要满足控制重启时已有通话继续，应实现独立媒体服务、有期限的续存租约、会话快照、重连认证、控制所有权代次及恢复对账。不能只删退出逻辑，否则会产生无法管理的通话与端口。整机或媒体进程崩溃后的接管仍是另一项能力。

**验收：**控制延迟、只读请求超时、控制进程重启分别注入；按设计验证存量 RTP 是否持续、准入是否关闭、恢复后是否重复分配或泄漏。该能力实现前，不能承诺控制故障下无业务损失。

3. 提高端口容量利用，并补异常呼叫清理

端口准入：分片选择 只比较活动通话数，没有考虑 Rust 已提供的 available_blocks。分配失败 后直接拒接并释放预留，不尝试其他分片。短通话集中在某一分片时，它可能活动数最低、端口却都在隔离期内，导致后续呼叫反复选中它；其他分片仍可能有空闲容量。配置检查 只保证全局 CPS 与端口隔离期的余量，不能保证各分片周转均匀。

**建议：**结合可用端口、在途分配及最近容量失败选择分片，对耗尽分片短暂停止准入，并针对明确容量错误做有界换片重试。统计有滞后，不能直接把上一秒的端口数当作当前可用配额；Rust 仍是分配的最终判断者。换片时保留原进程代次与请求身份，清理任何迟到成功分配。

**验收：**一部分分片长通话驻留、另一部分高 CPS 短通话持续周转，在保留端口隔离期的情况下验证剩余容量是否可用，且没有跨分片重复分配。

异常清理：workerFailed 只调用 sendByeB，但 B 腿未接通 时该函数直接返回。如果 B 已回过 180/183，A 收到媒体故障响应后，B 仍可能继续振铃，直到后续信令或对方自己的超时处理。

**建议：**已接通发送 BYE，尚未接通按事务状态发送或安排 CANCEL，继续保留迟到 200 的 ACK/BYE 清理。验收覆盖 180/183 后工作进程失败，以及失败与 200 同时发生。

4. 把容量工具改成真实业务负载与质量验收

callbench 等全部拨号完成后才开始 RTP，媒体全部停止后才统一 BYE。目前的 500 CPS 参数不能证明媒体满载时仍可保持 500 CPS 建拆。

下一版工具应同时提供：

  1. 接通即发媒体，持续维持目标活动数，按 CPS 不断替换通话；覆盖端口隔离、准入、定时器及事务回收。
  2. 每路、每方向、每个时间窗核对实际 PPS、最长断流与发包节奏。当前全场 98% 门槛 会掩盖局部负载不足。
  3. 记录发送及接收时刻，区分丢失包和超过播放期限的迟到包，统计 P50/P95/P99/P99.99、连续丢包长度、乱序与接通/拆线耗时。当前收尾继续等待 500 ms 收到的迟到包也计为成功，未证明实时语音质量。媒体 RTP 时间戳本身不能充当实际到达时间。
  4. 长时间运行的有界统计、周期汇总与故障注入；逐步覆盖 24/72 小时。当前工具限制一小时，不能仅延长参数而不检查内存、日志和单次最长通话配置。
  5. 已支持能力的组合负载：RTCP、DTMF、早期媒体、排空、单分片故障及过载；现有少量通话功能测试不代替满载验证。

Linux 到位后，发生器与服务端分机部署，双方采集 CPU、RSS、FD、socket 内存、NIC/内核丢包及软中断/队列证据。为现有采集器 增加这些字段及统一时间轴；关键证据缺失应报告“验收不完整”。区分发生器调度、端到端时延和服务器内部转发时延；跨机器单向时延需要同步时钟或校正方案。

容量预算应明确“一万路”的单位：当前一条桥接通话为两个呼叫腿、四个 UDP socket，即一万通话约两万通道、四万个服务端媒体 socket。以 G.711、20 ms、每包 160 字节音频计算：服务器每秒约接收 100 万 RTP 包并转发 100 万包；按 IPv4/UDP/RTP 总计 200 字节计算，收、发各约 1.6 Gbit/s，尚未计二层、RTCP、信令及其他业务。该算式是预算，不是实测吞吐。

5. 日志压力恢复与长期运行

journal.Record 遇到一次队列满就永久设置 failed。本轮使用 64 项队列复现：64 条已接受事件全部同步、队列归零后，健康状态仍为 false，后续事件仍被拒绝。因此暂时积压可以演变为持续停接和日志丢失。

拒绝继续准入体现当前保守策略，不能简单清除失败标记并忽略已经丢失的数据。建议分开维护“暂时积压”“存储失败”“已发生数据缺口”，在可恢复积压时控制流量，为结束事件保留预算；恢复准入前按明确策略处理缺口、恢复存储并完成对账。

另一个长期成本是 Open 每次启动逐行检查整个历史文件，时间随文件增长；当前无内置分段、保留策略及恢复检查点。应采用分段日志、序列号、检查点和校验后的归档策略，保留单写者与末尾修复约束。当前日志也未保存完整 SIP/媒体会话状态，不能直接用它实现在线接管。

**验收：**短暂积压恢复、队列满后的数据缺口、磁盘错误、异常断电尾部及大量历史文件分别测试，核对已接受/已写入/已同步/丢失事件，并限制启动恢复耗时。20 ms 的同步周期仍不是持久化零丢失保证。

6. 媒体与控制调度优化

发送重试：flush_pending 每轮只检查 128 个 socket；没有接收或控制工作时，循环等待 1 ms，发送队列期限却只有 5 ms。大量 socket 同时排队时，即使恢复可写，一部分也可能在获得重试机会前超期。有接收就绪工作时不会执行该固定等待，实际阈值受调度影响；这不能用来断言已定位既有压测丢包。

建议在有待发包时监听可写事件，结合最近截止时间安排重试，保留每轮时间预算和过期丢弃，记录排队时长。可写通知之后仍须处理 WouldBlock，就绪不保证下一次操作一定成功，参见 Mio Poll 官方文档。不要通过等攒满批次或无限扩大队列牺牲语音实时性。

控制循环：SIP send 在唯一业务循环中同步等待，单次最长 20 ms；批量消息和最多 1024 个到期定时器可能放大出口拥塞的影响。先增加循环延迟、命令排队、最老定时器迟到等指标；再考虑保序的有界发送队列、按耗时预算处理到期事件。当前没有测出 Linux 下的实际阻塞幅度。

原子媒体变更：连接式 UDP 更新 逐个连接四个 socket，中途失败没有回滚前面已变更的 socket。目前 Go 对当前版本错误会结束并释放通话，因此不能描述成普通流程长期留下断流会话。实现 re-INVITE/NAT 换址和失败后保留原通话之前，应补齐回滚或可恢复的提交状态机。

7. 根据实际热点减少每包开销

候选优化包括：

  • 每批共享时间采样，减少每包时间读取和浮点令牌补充。必须保持限流边界及发送期限；Instant::now() 不应被认定为必然进行内核系统调用。
  • 复用 Linux 接收描述符，计算平均批量 Δrx_packets / Δreceive_batches 和调用成本 Δreceive_syscalls / Δrx_packets。每个 socket 每 20 ms 一包时，实际批量可能接近 1。
  • 当前发送仍是逐包调用。同一接收批次、同一输出 socket 可评估批量发送，处理部分成功及顺序。不能跨不同 fd 拼成一次 sendmmsg，其调用指定单个 socket，且可能只发送部分消息，参见 Linux man-pages。也不能等待凑包。
  • 在 Linux 确认 CPU/NUMA、网卡队列与工作进程分布，检查真实 socket 缓冲占用及分片负载偏差。内核缓冲上限不等于预先全部分配的物理内存。

先保存 profiling 和每次变更的同条件对照结果，再决定是否需要更大范围的 I/O 架构调整。上述候选不附带未经测量的提升百分比，也不构成“加上某项技术即可万路”的结论。

8. FreeSWITCH 无感替换的落实顺序

兼容标准已有文档，但当前差距仍包括 ESL、XML、脚本、完整 SIP 和原生模块宿主。下一步应把标准变成可执行的差分验收，而不是继续增加文档页数。

固定 FreeSWITCH 1.11.3 参考构建，录制原客户端、配置、事件、话单和异常流程；同样输入分别执行原版与 RustSwitch，比较返回值、事件顺序约束、状态变化及媒体行为。先统一双通道 UUID、变量和生命周期模型，再实现 ESL/核心 API、XML/拨号计划、正式 SIP 提供器及业务模块。C/C++ 自定义编解码 ABI 不能计为旧 FreeSWITCH 模块二进制兼容。

性能矩阵也要按功能分别验收：纯转发、转码、录音、会议、脚本、ESL 订阅及外部后端压力有不同成本。纯 G.711 转发的一万路通过不能代表一万路全功能通过。所有未执行兼容用例继续保持未执行状态。

本轮证据与下一轮交付

  • 媒体命令乱序原始输出：3 次断言失败，暴露当前缺陷，不是通过的回归测试。
  • 控制超时复现：模拟 stats 延迟 1.2 秒后被终止；测试断言的是当前监管行为。
  • 日志积压复现：队列归零、全部已接受事件同步后仍拒绝记录；没有注入磁盘故障。

诊断在工作目录副本执行，原有 Go 文件与交付源码逐文件比对一致；新增测试和模拟进程仅位于工作目录。本轮没有复跑完整 Rust/Go/SIP 回归，原有测试结果不能代替新增问题的回归验证。

下一轮建议交付一个可独立验收的改进版本：完成同会话有序提交与媒体版本检查、超时分级、端口择片和故障 CANCEL 修复，并为这些路径补回归；同时升级混合负载与实时质量工具。控制面续存及 FreeSWITCH 差分框架单列里程碑。Linux 服务器到位后再确定媒体热点的实际优先级与万路容量结论。
