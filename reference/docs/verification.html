0.1 历史验证记录 · 2026-09-05

以下保留 0.1 时点的结果和待办，不代表当前源码状态。当前优化与验证见 0.2 报告。旧 Go 转发对照的标签错误已在本文和原始 JSON 中纠正。

结论

已形成可以构建和运行的 Rust 媒体、Go 控制面、C/C++ 编解码适配原型，基本通话及故障回归通过。尚未通过单机 1000 路无丢包测试，更未通过 10000 路生产容量验收。

本轮所有运行测试在同一台 macOS ARM64 开发机上完成，发生器报告 10 个可用逻辑 CPU。Rust 为 1.98.1，Go 为 1.27.1，使用 Apple Clang。Linux 只进行了编译检查；没有把 Mac 回环测试结果当作 Linux 物理网卡测试结果。

最终构建的 PCMA 测试同时确认媒体进程的 CPU 时间、峰值驻留内存统计能够返回，挂断后所有控制面呼叫和媒体分配均归零。PCMA 测试验证的是透明转发，不代表已完成实时转码。

1000 路分散相位场景中，Rust 应用层累计接收与成功提交发送的包数均为 1046368；来源拒绝、格式错误、包速率限制、发送错误及发送队列丢弃计数均为 0。发生器提交到媒体接收之间，以及媒体提交发送到发生器接收之间都有计数缺口。Mac 不支持本实现的 socket 丢包辅助计数，故不能据此证明内核没有丢包。

直连对照说明发生器在较短路径上可以完成本轮负载。**后续源码审计发现 --go-relay 只修改报告标签，没有建立 Go 转发层，故撤回该对照以及“问题并非 Rust 独有”的结论。**原始数字保留并标记为无效对照证据。现有证据不足以确定具体根因，需要进一步对齐主机分层计数、分析调度和 I/O，并在独立 Linux 压测机与目标服务器之间复测。

最初一次 100 路测试仅接通 99 路；当时尚缺少逐类失败记录，未能追溯该次失败的确定原因。随后增加了错误分类，修复了 RTP 65535 配合显式 RTCP 端口的解析边界，并补充回归测试；后续记录的 100 路测试通过。不能把后续通过当成首轮失败已被确定归因的证据。

已修正的实现问题

  • 发送给 A 端的 BYE 响应也必须按实际来源、Call-ID、From tag 和 CSeq 匹配事务。
  • SIGTERM 排空时等待未完成的 SIP 终止事务，避免首个 BYE 丢失后服务直接退出。
  • 旧媒体进程代次的控制命令不能进入重启后的新进程。
  • 占用端口导致整组分配失败时，关闭已打开的 socket 并有限次尝试其他端口组。
  • 发送端来源校验先于包速率配额，避免错误来源消耗正常端点的配额。
  • 本地发送压力缓冲有长度与时间上限，分别记录队列溢出及过期。
  • C ABI 先校验版本/结构尺寸前缀，再读取完整结构；销毁上下文后才卸载动态库。

下一阶段必须解决

  1. 定位 1000 路转发测试的丢包根因，建立独立 Linux 网络测试基线。
  2. 接入正式 C/C++ SIP 协议提供器并补齐协议互通，原型 Go 提供器不承担最终生产兼容性承诺。
  3. 完成动态过载准入、72 小时持续周转和故障注入验收。
  4. 逐项实现录音、转码、SRTP、ESL 等能力，并为每种组合重新测量容量。

交付中的最大并发配置、编译成功和单项测试结果，都不是“万路且零丢包”的证明。
