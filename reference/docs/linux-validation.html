Linux 容量与稳定性验收

本文件是 0.3 的后续验收步骤，不是已取得的 Linux 性能结果。linux-10000.example.json 中的 10000 是配置目标，不能作为容量证明。示例地址属于文档保留网段，部署前必须替换。用户将稍后提供服务器，本轮只交付源码、配置和工具。

设备和工作负载

  • 初始设备预算：32 个现代物理核心、128GB ECC、支持 RSS 的 25GbE 网卡。这是待测起点，不是已验证的最低规格或容量承诺；获得实际硬件后再选工作进程数。
  • 独立压测机：需要同时产生并接收预期包率。不要把发生器的瓶颈计为服务端容量上限，也不要忽略实际发包量不足。
  • 一路通话指两个呼叫腿、两个方向的持续音频，RTP 必须经过 RustSwitch。
  • G.711、20ms、相同编码的 10000 通话约为入站 100 万包/秒、出站 100 万包/秒。普通 IPv4 下分别约 1.6Gbit/s，不含链路和额外协议开销。
  • 每路使用四个端口，因此 10000 通话约占 40000 个 UDP 端口。500 CPS、2 秒端口隔离期还需约 4000 个端口余量。55000 端口的示例范围可满足此项账面预算，但仍应测量端口占用与各分片余量。

启动前

  1. 在 Linux 本机构建 Rust 与 Go 二进制，运行配置校验。当前本机的 Linux Rust 检查仅为交叉编译检查，不包含 Linux 运行验证。
  2. 核对文件描述符限制、物理核心/NUMA/网卡队列布局、网络 MTU、UDP 范围以及已有服务占用。明确保留媒体端口，避免和系统临时端口分配冲突。
  3. 先测不绑定 CPU 的基线，再按机器实际拓扑填写每媒体进程的 cpu_cores。将 Go 控制面、控制管道辅助线程与媒体核心合理分配。不要把超线程数量直接当作物理核心预算。
  4. 检查网卡 RSS/RX/TX 队列和 IRQ。只有定位瓶颈后才调整 RPS/XPS、缓冲和中断参数；本交付不会自动修改系统设置。
  5. 压测机默认每路四个 socket，10000 呼叫需要 40000 个 UDP 端口。发生器提供 --media-port-start 10000 --media-port-end 64999 显式分配，避免只依赖系统临时端口；媒体范围须预先排除其他业务使用。与服务端分机部署时可使用相同端口范围。共享端点诊断可用 --socket-groups 512，但必须单独标注，不能替代独立端点验收。
  6. 记录内核、驱动、CPU、内存、网卡、构建版本和全部配置。将主机指标与应用指标放在同一时间轴。

可直接运行的步骤

先在目标机项目目录执行：

make all
make test
make check
bin/rustswitch -check-config -config config/production.json
bin/rustswitch -config config/production.json

production.json 由 config/linux-10000.example.json 复制后填写实际 IP、上游、CPU 核心和日志路径。不要在旧服务仍占有媒体端口时启动第二份相同配置。系统服务模板在 deploy/rustswitch.service，创建服务用户与日志目录后再按实际部署路径安装。

另一个目标机终端启动只读采集器（替换 ens1f0，输出文件须不存在）：

python3 tools/collect_linux.py --interface ens1f0 \
  --admin http://127.0.0.1:9080 --seconds 180 --interval 1 \
  --output run/linux-1000-host.jsonl

采集器连续写入每核心 CPU jiffies、Linux IP/UDP 计数、网卡包/字节/丢弃/错误，以及应用状态；保留采集失败记录。它不修改网络参数、不自动判断容量，系统计数还包含其他进程。当前已验证解析样本，Linux 实际运行需在服务器上完成。文件描述符、驱动专用队列、内存趋势、IRQ/softirq 以及时间戳仍需补充采集，不能认为该工具已覆盖所有观测项。

独立压测机上，从 1000 路开始：

bin/callbench --server 198.51.100.10:5060 \
  --uas-listen 198.51.100.20:5070 \
  --bind-ip 198.51.100.20 --advertise-ip 198.51.100.20 \
  --calls 1000 --cps 100 --seconds 60 --connect-media \
  --media-port-start 10000 --media-port-end 64999 \
  --output run/linux-1000-generator.json

0.3 默认业务保护为最多 8000 路占用资源、1000 路建立中，并在占用达到 80% 后逐步降低新呼叫准入速率。开始容量实验前，先在管理页面查看并记录当前策略：万路实验需要在启动硬上限与端口预算允许的前提下，调整业务保护至实验规模，或在隔离验收环境临时关闭该额外保护。启动硬上限和媒体健康准入始终有效。容量测量结束后恢复业务保护，再单独执行超限拒绝与存量通话保持测试。不要把 503 保护拒绝误报成媒体处理容量不足，也不要把关闭业务保护的结果当作默认策略结果。

完成该档分析后，再测试 --calls 5000 --cps 500 与 --calls 10000 --cps 500，并相应延长主机采集时间。两个程序都应保留标准错误日志。--connect-media 只连接发生器端点，服务端通过配置中的 media.connect_sockets 控制；Linux 示例默认开启服务端连接。

同步对比服务器事件日志 call_established / call_ended 重建的并发，以及 /v1/status 采样。发生器的累计接通数可能包含已提前结束的会话，单独看该数不能证明同时在线。发生器退出非零、实际负载不足、采集缺失、清理失败、媒体工作进程重启都应判为未完成验收，保留记录再分析。

分阶段测试

场景 测试方法
功能闭环 先通过仓库中的 SIP/RTP/RTCP 和故障回归
容量爬升 1000 → 5000 → 10000；每档稳定后再提升
常规相位 callbench --spread=true，把各通话发包时刻分散到 20ms 内
集中突发 callbench --spread=false，集中发包；必须保留这一结果，不能用常规相位结果覆盖它
呼叫建立速率 单独提高到 500 CPS；检查 CPU、控制队列、事务内存和实际接通率
长时稳态与周转 使用持续建立/结束呼叫的 SIP 场景，10000 并发运行 72 小时
过载 额外增加新 INVITE，检查拒接、重传和已有通话媒体
故障 单个媒体进程退出、控制面退出、日志不可写、端口占用、网络抖动/乱序/丢包

当前 callbench 是单轮建立、维持、结束工具，媒体时长最多 3600 秒，尚不能独立完成 72 小时持续周转验收。需增加长期发生器或使用 SIPp 等专用工具，并核对媒体流量是否真实持续。

服务端最大通话时长从每路收到接通 ACK 起计算，最早接通的呼叫还会经历其余呼叫的建立阶段。长测时应将 sip.max_call_seconds 设为高于整批建立耗时、媒体维持时长与清理余量之和，并同步调整服务模板的 TimeoutStopSec，避免人为时长上限打断测试。

必须同时记录

  • 成功接通、失败状态码、实际并发、CPS 和通话时长分布。
  • 发生器名义包数、实际成功提交包数、对端唯一接收数、重复/乱序/内容错误、发生器调度延迟。
  • 每个 Rust 进程的接收/发送计数、socket 丢包、来源拒绝、包率限制、发送队列溢出和过期计数。
  • NIC 和驱动丢包、Linux UDP 接收错误、CPU softirq、每核心利用率、内存、文件描述符及端口回收。
  • 日志写入数、持久化数、积压和丢失数。异步事件日志的持久化窗口应实测，不承诺 RPO=0。
  • 服务端新增转发延迟 P99/P99.99。明确使用软件时间戳还是 NIC 时间戳，不能把发生器调度延迟算成服务端处理延迟。

准入条件

目标负载下要求实际发包量达到测试设定，服务器引入的可观测丢包为零、异常掉话为零、无持续资源增长，并保留处理余量。故障注入允许的影响范围需单独约定。

0.2 已实现静态资源预留、CPS、分片配额与媒体包率限制，并增加按媒体进程 CPU、控制积压、socket/发送丢包增量和统计新鲜度的动态准入。默认高/低 CPU 门限为 0.85/0.65 个核心，恢复需连续三个健康样本。该机制只控制新呼叫，不能补回已经丢失的 UDP 包。

媒体进程 CPU 不是最忙物理核心指标；NIC 全局丢包、内存压力和尾延迟尚未自动反馈到准入。SO_RXQ_OVFL 依赖后续接收的数据报携带计数，缺少新数据时可能未及时显现；连接式 UDP 的内核来源过滤也可能不进入应用拒绝计数。单次流量测试通过不等于完整可靠性验收。

先结合 receive_syscalls / receive_batches / max_receive_batch 确认批量接收收益，再决定是否实现批量发送、进一步减少时钟读取、共享 socket、io_uring 或内核旁路。当前不把这些未实现手段计入容量结论，也不自动修改 RSS、IRQ、缓冲或系统端口设置。

参考原始规范：RTP、SIP 过载控制、Linux 网络多核处理、recvmmsg、sendmmsg。
