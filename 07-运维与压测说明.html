07 RustSwitch 运维与压力测试

本章说明容量保护、日常观测、隔离测试、故障处理和升级验收。适用于当前主工程；候选专有事项会明确标注。测试结果需要同时记录版本、配置、环境与完整业务负载，不能将本地模拟、历史探针或构建成功用作生产容量结论。

容量保护的实际语义

启动硬限制控制 max_calls、calls_per_second、burst_calls、事务和端口预算。Guard 在硬限制内提供在线调整的新呼叫保护；不能通过页面把硬上限提高到启动配置之外。

指标或参数 实际语义
active_calls 已预留且尚未释放的呼叫资源，不等于全部已接通通话
established_calls 已达到正确 ACK 建立条件的通话数
establishing_calls active_calls - established_calls 的饱和差值，还可能包含等待释放的资源
calls_per_second 新呼叫令牌的补充速率，不是并发数量
burst_calls 令牌桶容量，限制瞬间进入的新呼叫数量
accepted / rejected Guard 允许/拒绝的准入检查次数，允许不代表最终接通

初始 Guard 策略取活动上限 min(8000, max_calls)、建立中上限 min(1000, max_calls)、CPS min(1000, calls_per_second)；Guard 突发值还会被硬突发值及其 CPS 收紧。因此本地示例实际是 100 路活动/建立中上限、20 CPS、20 个 Guard 突发令牌，启动硬突发值为 40。

软阈值默认 80%，达到后逐步降低新准入补充速率，最低默认 10%；达到硬阈值或令牌不足时返回 SIP 503 与 Retry-After。被拒绝呼叫不会排队等待接通，已有 ACK/BYE 等后续信令不套用新呼叫限速。实际负载下的媒体与信令时延仍需观测。

分片自适应准入还根据实际 CPU 增量、可观测丢弃、队列积压和统计过期暂停新分配，连续健康样本后恢复。保护有效不等于所有目标负载都可零丢包。

调整时先保存完整旧策略，再逐步改变单一参数，观察拒绝原因、当前有效 CPS、最忙分片和媒体结果。降低上限不会主动挂断存量通话；已有资源可能暂时高于新阈值。反复保存或开关保护不会自动补满令牌。

日常观测入口

入口 运维用途 解释边界
/healthz 检查控制进程能否响应 不代表线路、媒体或依赖健康
/readyz 查看瞬时新准入状态，受排空、日志、Guard 和媒体健康影响 503 可能是保护行为，不一定是进程故障
/v1/status 查看通话、注册、worker PID/代次、计数、日志和配置状态 多类统计可能来自不同采样时刻
/metrics 获取 Prometheus 文本指标 监控采集端和告警规则需部署方提供
/v1/config、/v1/guard 核对 active/desired、revision 和当前保护策略 CSRF token 属于当前控制进程，不应写入公开报告
/v1/tests 及任务详情/报告 观察隔离测试、采样和清理 主业务指标和测试实例指标必须分别记录

下面只读查看就绪状态及业务快照，不创建测试：

curl --silent --show-error --include http://127.0.0.1:9080/readyz
curl --fail --silent --show-error http://127.0.0.1:9080/v1/status
curl --fail --silent --show-error http://127.0.0.1:9080/metrics

关注趋势和增量，同时记录进程 PID、worker generation 与采样时间。重启后的计数重置、过期缓存和未提供指标应分别处理，不能统一填成 0。

正确执行压力测试

运行前确认当前没有其他活跃测试，且被测机有足够 CPU、内存、文件描述符和隔离端口。网页测试通过固定参数创建自己的进程，不接受任意远端主机、可执行文件或磁盘路径；它不是任意目标的通用负载平台。

  1. 单路 SIP/媒体试用，核验两方向实际音频和挂断回收。
  2. 先验证正常 Guard 下的拒绝行为，再在隔离容量模式下测承载。两种报告分别判断。
  3. 由小到大增加并发/CPS/持续时间；500/1000/2000/3000/5000/自定义只是参数档位。
  4. 每次保存唯一原报告、配置、发生器和被测程序身份、分片采样、端到端逐流结果及清理状态。
  5. 目标 Linux 机器上重复基线与候选的等价业务，持续验证 CPU、内存、最忙分片、发送尾延迟与音质。

网页 API 是隔离模拟测试，不呼叫真实运营商号码。下列命令从公开仓库根目录执行，需要后台已经启动；脚本默认会创建单路和停止流程测试，因此不是只读探测：

mkdir -p ../rustswitch-test-results
testlab_result="../rustswitch-test-results/testlab-$(date +%Y%m%d-%H%M%S).json"
python3 source/main/tests/testlab_e2e.py \
  --url http://127.0.0.1:9080 \
  --output "$testlab_result"

默认测试为 PCMU 单路三秒及媒体阶段停止流程，不自动加入 5000 路负载。输出父目录必须存在，报告路径应唯一，保留失败原件。脚本遇到已有活跃测试会拒绝执行，不会主动停止其他任务。

需要压力场景时，先确认资源和变更窗口，再显式增加参数。例如以下命令会在默认场景之外再执行 500 路、100 CPS、10 秒的媒体测试：

testlab_result="../rustswitch-test-results/pressure-500-$(date +%Y%m%d-%H%M%S).json"
python3 source/main/tests/testlab_e2e.py \
  --url http://127.0.0.1:9080 \
  --output "$testlab_result" \
  --pressure-calls 500 --pressure-cps 100 --seconds 10 --timeout 300

参数范围由脚本校验：压力路数 1–10000，CPS 1–1000，媒体时长 1–300 秒，每阶段等待 30–900 秒。--seconds 不包含全部建呼时长；以上范围只是工具输入边界，不是已验收容量。单任务也不等于 72 小时长稳测试。

后台只有受控的单个活跃测试槽位。任务采用 request_id 去重，该标识只在当前控制进程生命周期有效；完整历史报告最多保留 20 份，幂等键最多 4096 个。及时下载需要保留的报告，历史淘汰或进程重启后不要假设还能找回完整任务数据。

通过条件与计数

项目 需要核对
建立 请求数量、实际建立数量、原因分类、真实接通峰值
负载 总体和每路每方向达到名义包量要求，不能只对少量成功包算零丢包
音频 逐流/双向唯一接收、内容、编码、序号/时间戳和串音检查
期限 发生器迟到、发送超期、端到端到达窗口、队列年龄
清理 发生器、控制/媒体子进程退出、媒体端口释放、专属工作目录收尾
证据 当前源码、二进制、配置、原始输入输出、执行时间及未跳过的断言

sent_packets 是发生器成功交给本机发送接口的数量；received_unique_packets 才是校验通过的唯一接收。Rust rx/tx 是媒体节点视角，不能直接与其他不同时刻的缓存快照相减定位一跳丢包。UDP submit 也不表示远端听到。

报告的 result 只有在发生器输出完整有效结果时才存在；缺失结果不是零丢包。cleanup.complete 表示相应清理检查完成，不能把原有媒体失败改成成功。CPU、内存要按控制进程、Rust 媒体与发生器分别观察，不能只看页面中某一组进程就计算全系统成本。

已知历史结果与诊断缺口

2026-09-07 保存的真实 2000 路 Darwin relay 记录：2000 路均建立，发送 2,000,000 包，唯一收到 456,233 包，接收率 22.81165%，仍是失败。5000 路另一记录未通过本机隔离端口预检，未启动。它们不是 Linux 生产容量成绩。

历史审查发现：失败结束时统计可能未刷新；不支持的 socket 丢弃计数可能显示 0；计数与时间分开发布可能不一致。相关诊断补丁分别保留在 source/patches/，其中已测试快照与后续工作稿有不同验证范围，不能自动作为主工程已合入修复。资料不会把统计说明或未合并补丁改写成高并发通过。

具体数据、观察时刻及归因限制见 2000 路失败记录的只读审查。这是历史失败分析，不是本次重新运行结果；其中原始路径和源码行号用于描述当时记录。

Linux 支持本实现的 SO_RXQ_OVFL，Darwin 不支持；未提供/未知必须与真实零值区分。下一步仍需要同条件直连/relay/Linux 对照、实际 socket 缓冲、媒体窗口资源增量及批内发送延迟，才能定位瓶颈。

日常观测与故障排查

现象 检查顺序与处理
后台读取失败 healthz/网络可达 → HTTP状态 → 当前任务ID是否已过期 → 详情/报告独立错误；不要自动重复创建任务
503 拒绝新呼叫 排空/停止 → Guard原因 → 硬并发/CPS → 事务/端口 → 日志健康 → worker准入
注册失败 实际上游IP/端口/传输 → realm/账户 → 私有文件权限 → 有效期/挑战次数/来源匹配
已接通但无声音 正确ACK → 两方向SDP/白名单 → RTP/RTCP端口 → PT/clock/ptime → 接收/发送/期限和对端实际接收
IVR没有结果 真实UUID/已ACK资格 → 应用受理 → 完成事件关联 → read_result与结束原因；+OK不是完成
ASR槽不回收 仅候选：起建/未知RX → 实际退订/退休 → Closed；普通context取消不能独自证明远端资源不存在
通话数归零但计时器非零 等待协议规定的有限重传/清理窗口后再判定；不可立即删掉所有合法缓存
worker崩溃 记录故障分片与代次，核对其通话终止，观察自动重启；不承诺该分片通话无损
5000预检端口不足 使用独立地址/压测机及明确端口规划；不能占用主服务媒体范围强行启动

针对“读取失败”，先区分三个阶段：请求尚未成功读取、任务已经失败、发生器没有完整结果。优先保留任务 ID，分别读取列表、详情和报告；记录 HTTP 状态与机器可读的 failure.stage/failure.code。403 可能涉及 CSRF/访问边界，409 可能是任务冲突，410 可能是历史记录已淘汰；不要因为页面重试就创建新的压力任务。

针对端口预检失败，核对 processes_started：未启动进程时不能称为已经完成该并发的媒体验收。调整隔离地址或发生器部署后，应使用新的、明确记录的测试环境重新执行；改变主服务媒体范围来强行通过预检会破坏隔离前提。

持久化、升级与验收层次

日志单写者、批量 fsync；有界积压会影响准入，不能承诺掉电零丢失。管理文件在 journal.path 后追加 .admin.json，保存 desired/Guard/XML；HTTP 不改写原始启动 JSON，配置工作区也不自动执行 FreeSWITCH XML。

升级前保存程序哈希、启动 JSON、管理状态和对应许可，准备回滚组合；排空并确认进程退出后再替换程序。回滚同样需要核对待启动状态，避免旧程序意外读取新版本保存的配置。服务账户、日志空间、文件权限和 systemd 限额按 使用说明 检查。当前不支持将活动通话状态无损迁移到另一版本或主机。

验收顺序为：单元/竞态 → 真实协议媒体 → 精确原版差分 → Linux同机等价性能 → 长稳/故障 → 小流量灰度/回滚。Go测试事件数量、HTTP操作数量、原始目录条目和可运行原版模块是不同分母，不能相加或用一种替代另一种。

每份正式验收报告至少应包含：固定的两侧程序身份、配置和已加载功能，CPU/内存/网络规格，发生器部署，编码与包时长，建呼速率和媒体时长，每方向逐流结果，资源窗口增量，失败分类，清理状态及未覆盖范围。5000/10000 路、长期混合负载和完整真实语音智能体仍以 需求说明书 与 未完成清单 的验收条件推进。
