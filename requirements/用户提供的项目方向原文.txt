我会把这个项目定义成：**“云蝠高性能实时语音内核”，而不是“用 Rust 完整复制 FreeSWITCH”。**

核心要求是：

> **在相同服务器、相同音频质量、相同业务功能下，提高稳定媒体并发，降低每通电话的资源消耗，并把高负载下的声音卡顿、打断延迟和异常影响范围控制住。**

先收紧前面的性能判断：**1.5～3 倍不是已有实测结论，只能作为优化探索范围。** 正式立项应先测现网基线，再冻结验收目标，不能把“换成 Rust”本身当作收益保证。

下面这套内容可以作为研发需求和架构评审的基础。

# 一、项目定位与首期边界

**建议项目名称：云蝠 Voice Runtime。**

技术分工仍然采用：

| 层级 | 建议技术 | 职责 |
|---|---|---|
| 实时媒体内核 | **Rust** | RTP、音频调度、编解码、重采样、播放、打断、音频分发 |
| 业务控制层 | **Go** | 呼叫任务、路由、智能体编排、租户配置、业务接口 |
| SIP 接入层 | 优先复用经过验证的实现 | SIP 会话、SDP 协商、线路兼容、呼叫生命周期 |
| 编解码与 DSP | Rust 接口封装成熟实现 | 不为“纯 Rust”重新发明全部编解码器 |
| 生产部署 | **Linux 优先** | 明确 CPU、网卡、内核和部署配置的性能基线 |

**第一期只围绕电话 Voice Agent 闭环建设，不做通用 PBX 大全。**

会议系统、视频、传真、复杂分机管理、完整 Dialplan、任意脚本插件市场，都不应进入首期。

SIP 协议栈可以逐步替换，不要求与媒体内核同时从零重写。若过渡期保留 FreeSWITCH 承担部分接入功能，压测必须把它占用的资源一起计入，不能把成本移到另一个进程后宣称性能提升。

# 二、性能目标：以“有效稳定并发”为核心

我建议采用以下**初始研发目标**。这些数值是拟定的验收门槛，不是当前已经达到的性能。

| 指标 | 建议目标 | 统计口径 |
|---|---|---|
| 完整 Voice Agent 稳定并发 | **达到现网基线的 1.5 倍**，进阶目标 2 倍 | 功能、音质、延迟门槛相同 |
| 单位通话 CPU 消耗 | 同并发下下降 **≥30%** | 包括媒体、接入适配、录音和相关内核开销 |
| 内存占用 | 同并发下下降 **≥30%** | 缓冲时长、录音方式和功能配置一致 |
| 媒体发送调度迟到 | **P99≤2ms，P99.9≤5ms** | 在指定硬件、受控网络及目标负载下测量 |
| 稳定性 | **72 小时混合负载运行** | 包含建呼、挂断、打断、录音与异常注入 |
| 媒体正确性 | 无串音、无旧回复复播、无无法解释的音频缺口 | 不允许只统计“连接还在” |

这里的“调度迟到”，指**已经具备发送条件的音频包，相对计划发送时刻晚了多久交给内核**。它不是用户听到声音的总延迟。

Jitter Buffer、TTS 预缓冲、网络传输和终端播放缓冲必须另外计量。RTCP 中的 interarrival jitter 也不是这个指标，不能混用。

**性能验收的前提始终是：不能靠降低音质、关闭录音、减少安全能力，或者丢弃用户语音来换并发。**

# 三、线程模型：一个媒体会话，一个明确的状态所有者

这是我最优先写进需求的架构约束。

## 3.1 采用固定数量的媒体 Worker

每个 Worker 负责一组媒体会话，同一个会话的 RTP 状态、编解码状态、播放状态和打断状态，原则上由同一个 Worker 修改。

不采用“一通电话创建一个操作系统线程”，也不让同一会话的音频帧在全局线程池中反复迁移。

同一通桥接电话的两条媒体腿，应尽量分配到同一个 Worker；确实需要跨 Worker 桥接时，必须有明确的队列、时延和资源预算。

**首期不做活跃媒体会话的自动迁移。** 新呼叫根据 Worker 的剩余处理能力分配，已有会话保持稳定归属。

## 3.2 媒体线程不等待外部系统

媒体 Worker 内禁止出现同步数据库访问、磁盘写入、HTTP 请求、等待 ASR/TTS 返回，以及等待业务锁的逻辑。

轻量编解码和基础音频处理可以在 Worker 内完成；重型降噪、复杂模型推理等任务进入**有并发上限、有截止时间的独立执行池**。

Tokio 可以用于网络适配和控制接口，但不应默认把所有音频处理都塞进通用 Tokio 调度器。Tokio 的任务调度具有协作式特征，CPU 密集工作和阻塞调用需要单独约束；也不应每处理一帧就调用一次 `spawn_blocking`。

## 3.3 Worker 必须有公平调度与执行预算

每次处理收包、发送、控制命令和音频任务，都应设定最大工作量，防止某一路异常流量占满整个 Worker。

打断、挂断等控制命令应有独立的处理预算，不能排在大量普通音频任务之后；同时也不能让控制命令洪峰饿死 RTP 收发。

CPU 亲和性、网卡队列、IRQ 与 NUMA 内存布局应作为可配置的部署能力，并通过压测选择配置。Linux 的 RSS、RPS、RFS、XPS 各有不同作用，不应不加区分地全部开启。

# 四、网络 I/O：优化真实的小包处理成本

## 4.1 先明确 socket 和端口模型，再谈批量收发

要求提供可复现的网络 I/O 基准，覆盖实际线路使用的 RTP 端口分配方式。

基础实现建议采用非阻塞 UDP 和事件驱动收发，按实际收益使用 `recvmmsg`、`sendmmsg`。

但这里有一个重要限制：**这两个接口每次操作的是一个 socket，并不会自动把几千个不同 RTP socket 的包合并处理。** 若每通电话使用独立端口，单个 socket 又只有每秒几十个包，批量收益必须实测。

因此，需求应写成：

> 根据线路兼容性确定独立端口或共享端口模型，并证明其收包分发正确性、单核处理能力与多核扩展能力。

不能为了批量收包，擅自假设所有线路都支持共享媒体端口。

## 4.2 批处理不能以额外音频等待为代价

允许批量处理**已经到达或已经到发送时刻**的包，不允许为了凑满一批而等待下一帧。

发送端必须保留逐包发送节奏，不能把几百毫秒的 TTS 音频一次性灌进发送队列。

接口实现还必须正确处理部分发送成功、缓冲区不足、突发包、重复包和非法包。

## 4.3 高级网络方案作为可替换后端

建议保留 `io_uring` 后端的接口位置，并与基础实现进行对照测试，而不是预设它一定更快。

AF_XDP、DPDK 等更激进方案，只在性能分析证明网络收发已经成为主要瓶颈时进入下一阶段。AF_XDP 的零拷贝能力还受到网卡和驱动支持情况影响，不能作为所有部署环境的默认前提。

**验收看同音质下的总 CPU、吞吐和尾延迟，不看用了多少“高性能技术名词”。**

# 五、内存与 Audio Graph：少分配、少转换、少跨线程

## 5.1 稳态热路径以不分配通用堆内存为目标

会话建立时预分配必要的媒体状态、帧缓冲、抖动缓冲和队列容量。

要求通过工具实际统计 RTP/PCM 热路径的分配次数，而不是代码评审时声称“应该没有分配”。第三方编解码库的内部行为也必须纳入检测。

缓冲池耗尽时必须有明确策略，禁止在高负载时无限扩容。

## 5.2 不把 `Arc<AudioFrame>` 当作默认最优解

同一个 Worker 内的音频消费者优先使用借用、局部所有权或缓冲池句柄。

跨线程传递时，再根据实际成本选择共享缓冲或一次受控复制。`Arc` 的引用计数使用原子操作，并不是免费的；不跨线程时，没有必要到处使用原子共享。

尤其要防止：

> 录音或 ASR 消费变慢，长期持有媒体缓冲，最终把实时收发使用的内存池耗尽。

为了隔离慢消费者，复制一次到专属队列可能比追求端到端零拷贝更合理。这个选择必须由压测决定。

## 5.3 统一音频对象，不强制统一为 16 kHz

这里需要调整前面“内部全部使用 16 kHz PCM”的建议。

**应该统一的是 AudioFrame 的接口、时间语义和生命周期，而不是所有节点的采样率。**

AudioFrame 至少需要明确：采样率、声道数、样本格式、有效样本数、媒体时间位置，以及丢包补偿等状态标记。

建议采用这样的处理方式：

```text
G.711 电话输入 → 解码为 8 kHz PCM
                    ├─ 按需要供录音、检测使用
                    └─ ASR 要求 16 kHz 时，在 ASR 分支重采样

TTS 返回 24/48 kHz 音频
                    └─ 在电话输出分支按目标编码要求转换
```

同一方向、同一音频区间，避免重复解码；多个消费者要求相同目标格式时，尽量复用转换结果。

同时，**音频采样率与 RTP 时钟必须分开建模**：G.722 的实际音频采样率是 16 kHz，但 RTP 时钟为 8 kHz；Opus 的 RTP 时钟则固定为 48 kHz。

## 5.4 Audio Graph 在配置时准备，不在每帧临时拼装

建议首期采用有限的、经过验证的处理节点和图模板。

会话建立或配置变化时，提前完成节点校验、缓冲准备和执行顺序生成。热路径只执行准备好的处理链，不做动态配置查询、脚本解释或临时资源加载。

图变更应在明确的帧边界生效，并有配置版本，避免一帧音频同时使用新旧参数。

# 六、首期功能要求

| 模块 | 首期必须达到的能力 |
|---|---|
| 电话接入 | 呼入、呼出、接听、挂断、早期媒体、超时处理，以及目标线路的 SDP 协商 |
| 编解码 | **PCMA、PCMU、G.722、Opus**；其他编码按真实线路需求加入 |
| RTP/RTCP | 收发、序列号与时间戳处理、乱序、重复、丢包、基础质量统计 |
| DTMF | telephone-event 收发、协商、重复事件去重；带内检测按业务需要启用 |
| 音频处理 | 重采样、基础增益、播放、混音、VAD、丢包补偿、可配置抖动缓冲 |
| AI 媒体接口 | 流式 ASR 上行、流式 TTS 下行、连接状态与错误事件 |
| 通话控制 | 打断、停止播放、播放完成事件、桥接及转人工所需的最小能力 |
| 录音 | 收发双轨、时间对齐、异步写入、完整性与失败状态 |
| 安全与隔离 | 接口鉴权、租户隔离、媒体来源校验、按接入要求支持 TLS/SRTP |
| 运维能力 | 容量限制、健康检查、停止接新呼叫、存量通话排空、指标与诊断 |

telephone-event 的处理应按协商结果进行，不能把载荷类型固定写死为某一个数字；事件持续时间和结束标记也要正确处理。

G.729、AMR-WB、EVS 是否进入首期，以实际线路接入需求为准，不为“编码数量多”投入研发。

**完整 WebRTC 接入单独设里程碑。** 支持 Opus 不等于已经支持 WebRTC，后者还涉及媒体安全、连接建立等协议能力。

# 七、Voice Agent 专项：打断与时间线必须是一等能力

## 7.1 收音与播音始终独立

播放 TTS 时，必须持续接收用户语音，并按配置运行 VAD、ASR 和打断判断。

ASR 默认使用对端接收轨道，不能误把混合录音或自己的 TTS 播放轨道当作用户输入。回声处理和误打断应有独立测试集。

LLM、知识库和业务工具不进入实时媒体 Worker。媒体内核负责音频连续性与确定的控制动作，业务层负责对话决策。

## 7.2 打断不能只停掉当前播放器

每轮回复必须具有可校验的 `turn_id` 或生成版本号。

打断确认后，媒体侧应立即让旧版本音频失效，清理尚未发送的旧播放内容，并拒绝随后迟到的旧 TTS 数据。上游取消请求可以同时发出，但**不能等模型服务确认取消后才停止本地播放**。

发送前还要进行最后一次版本检查，避免旧音频已经排队后又被发出去。

打断不应随意重置当前 RTP 会话的序列号和媒体时钟。

## 7.3 淡出是可配置的音频动作，不是固定等待

建议支持立即停止和短淡出两种方式，初始淡出参数可以从 **20ms** 开始调优，而不是一律增加 100ms。

打断指标必须拆开：

**用户开始讲话 → 系统确认打断 → 媒体侧开始停止旧音频 → 最后一个旧语音包发送。**

已经进入网络或对端播放缓冲的声音无法由本地取消，所以不能把“本地队列清空”宣传成“用户端立即静音”。

同时应记录“已生成、已接收、已发送”的回复进度，供对话层估计用户可能听到了哪里；不能把整段已生成文本都当作用户已经听完。

# 八、缓冲与过载：宁可明确降级，不要积压成延迟

**所有队列必须有容量上限，并同时暴露队列长度和最老数据年龄。**

对于音频队列，不能只配置“最多 1,000 条消息”，还应能配置最多缓存多少毫秒音频、占用多少字节。

| 队列 | 满载时要求 |
|---|---|
| RTP/实时处理队列 | 记录内部丢帧与超时；触发容量保护，不能无限积压 |
| ASR 上行队列 | 触发明确的语音缺口、流重置或业务降级事件，不能静默删掉用户说话 |
| TTS 播放队列 | 限制超前生成与接收，必要时取消后续生成；不能随意丢掉一句话中间的音频 |
| 录音队列 | 使用有界缓存和写入策略；写入失败必须显式上报 |
| 日志与诊断队列 | 允许限流、采样或丢弃非关键诊断，不能阻塞通话 |

Jitter Buffer 应支持按线路设置最小值、目标值和上限，并测试不同网络条件。不能为了低延迟一律关闭缓冲，也不能遇到丢包就无限增加等待。

丢包、静音、DTX 与补偿音频应尽可能保持可区分的状态。Opus 的带内 FEC 可能需要利用后一个包恢复前一个包，因此恢复能力与等待时间之间需要明确取舍。

容量保护应同时观察最忙 Worker、发送迟到、缓冲池水位和队列年龄，而不仅是整机平均 CPU。

达到高水位后，优先拒绝新呼叫，保护存量通话。必要录音发生不可恢复故障时，是继续通话还是结束通话，必须由业务策略明确决定，不能悄悄关闭录音。

# 九、可靠性：把故障范围和恢复边界写清楚

建议将媒体运行时部署为少量独立进程，每个进程包含若干 Worker；进程数量与 NUMA 布局、故障影响范围一起评估。

不应承诺“一个 Worker 崩溃只影响一通电话”。**需求必须明确一个进程故障最多影响哪些会话，以及其他进程如何继续服务。**

控制接口需要请求幂等、事件序号、会话版本和断线后的状态同步。重复的停止播放、挂断或录音命令，不能造成错误状态。

升级和回滚以**新呼叫切流、旧呼叫排空**为默认路径，不把进行中的通话无损迁移作为首期承诺。

协议解析、媒体来源识别、端口复用和 FFI 边界必须进行异常输入测试。收到畸形包不能触发无限分配、死循环或影响其他租户。

# 十、压测要求：不能只交一张“最大并发”截图

## 10.1 分开测试三类媒体场景

必须分别报告纯媒体转发、编解码处理、完整 Voice Agent 链路。

FreeSWITCH 本身已有 proxy media 和 bypass media 模式：前者可以不解码地转发媒体，后者让 RTP 不经过 FreeSWITCH。因此，不能拿新系统的纯转发容量去对比旧系统的完整 AI 处理容量。

主验收场景应当是：

> 实际电话编码 + 真实音频输入 + ASR 流式上行 + TTS 流式下行 + VAD + 打断 + 录音。

第一轮使用行为可控的 ASR/TTS 模拟服务隔离外部波动，但必须保留实际协议、连接和音频传输成本；第二轮再接真实供应商验证端到端效果。

## 10.2 固定比较条件

新旧系统使用同一服务器和等价的 CPU、网卡、系统资源配置；固定编码、ptime、通话时长分布、录音格式、加密开关、网络条件及业务功能。

同时提供“优化后的 FreeSWITCH 配置”作为对照，避免只击败一个没有调优的旧部署。

媒体并发和 CPS 必须联合测试：不能分别测出两个峰值，再把它们拼成一个同时可达的容量参数。

## 10.3 必须有故障注入与音频正确性检查

除正常稳定负载外，要测试集中建呼与挂断、突发 TTS 返回、ASR 停止读取、录音磁盘变慢、网络乱序与丢包、控制面断连。

音频不能只发静音。应覆盖连续语音、双方抢话、短回答、长回复、频繁打断、DTMF、长时间通话和不同采样率切换。

报告同时包含 CPU、内存、PPS、各 Worker 负载、队列年龄、缓冲池水位、内部丢帧、发送迟到、录音完整性和 ASR 识别效果。

逐包日志默认关闭；指标在 Worker 内局部累计后异步汇总。单通电话详细追踪采用限时、限量诊断方式，避免观测功能本身改变容量结论。

## 10.4 容量规划必须包含网卡与磁盘

按持续发送、20ms 一个 RTP 包计算：

**每条单向流是 50 包/秒；单腿双向电话是 100 包/秒，1 万路就是约 100 万包/秒。** 双腿桥接则约为 200 万包/秒，尚未计入 RTCP 和 AI 服务通信。

录音也不能忽略。假设每通电话保存双轨、16 kHz、16-bit 未压缩 PCM，则：

**每通约 64 kB/s；1 万路约 640 MB/s，约 2.3 TB/小时。**

这些只是按指定格式计算的资源量，不是容量承诺，但足以说明：**媒体 CPU 优化成功后，录音吞吐仍可能决定整机容量。**

# 十一、实施顺序与交付标准

我建议按验证结果推进，而不是一次性重写全部模块。

| 阶段 | 重点 | 通过条件 |
|---|---|---|
| **阶段 0：现网基线** | 测清 FreeSWITCH 的 CPU、线程、网络、录音和音频链路 | 能解释当前容量主要受什么限制 |
| **阶段 1：单 Worker 媒体闭环** | G.711 收发、播放、时间线、基础缓冲 | 音频正确，单核性能可复现 |
| **阶段 2：完整 AI 闭环** | ASR、TTS、全双工、打断、双轨录音 | 功能和音频质量达到对照要求 |
| **阶段 3：多核扩展** | Worker 分片、NUMA、网络 I/O、容量保护 | 达到约定并发与尾延迟目标 |
| **阶段 4：生产替换** | 线路互通、异常测试、灰度、排空、回滚 | 满足稳定性和运维门槛 |

最终交付不能只有源码。至少要有**模块与接口契约、线路互通清单、可复现压测脚本、容量报告、部署调优说明，以及故障降级和回滚手册**。

---

**我最建议写进立项书的核心要求是：**

> 采用 Rust 构建面向 Voice Agent 的实时媒体内核，以单会话状态单写、固定媒体 Worker、有界内存与队列、按需音频转换、可取消的播放时间线和明确的过载保护为核心。媒体热路径不依赖数据库、磁盘或模型服务及时响应。在与现网等价的功能、音质和部署条件下，以稳定并发提升 50% 为初始目标，并通过尾延迟、音频正确性、故障注入和长期运行测试验收。

**优先级应当是：音频正确与稳定 → 单核效率 → 多核扩展 → 内存与复制优化 → 更激进的网络后端。** 先证明每一步的收益，再增加复杂度。
